# 実験用Sessionの登録取消：研究者向け運用手順

> 対象は `SBKB_INTEGRATION_V1` の**実験用4活動Session**です。この機能は**物理削除／研究データの消去ではなく、未開始Sessionの登録取消（論理削除）**です。旧 `STAGE1_4` / `STAGE1_5` / `STAGE1_6` のデータ削除とは別の仕組みです。

本リポジトリは合成データを使う開発・模擬研究用プロトタイプです。実参加者データや本番研究DBでの操作を前提としていません。詳細な注意は [README](../README.md#安全上の注意と運用制約) を参照してください。

## 取消の目的と適用条件

準備中の実施に誤って登録した、**学習が始まっていない参加者Session**を通常運用の対象から外すための操作です。

次の条件を**すべて**満たす場合に限り登録取消が認められます。

- 実施状態が `PREPARING`（準備中）。`RUNNING`（実施中）・`ENDED`（終了済み）は不可。
- Sessionが `NOT_STARTED`（未開始）で、開始・終了時刻が記録されていない。
- 端末登録候補が**1件もなく**、有効端末の割当もない。端末切替で有効端末を外しただけでは取消できません。
- Stageの進行、保存Map、研究イベント、学習者操作、受信・配信記録、回答、振り返り等の学習関連記録がない。
- 現在のアクセスコード世代が画面で確認した世代と一致し、同じSessionが取消済みでない。

画面では実施状態・Session状態・端末登録・Stage状態に基づいてボタンを制御し、**APIとDBトリガーが実際の記録を再検査**します。画面で選択できても、競合や追加記録が発生していればサーバーは拒否します。活動開始後のSessionを削除する機能ではありません。

## 研究者画面での操作

1. 研究者コードでログインし、対象の**実施詳細（参加者管理）**を開きます。実施状態が「準備中」であることを確認します。
2. 「**セッションの削除**」欄の説明を読み、「登録を取り消す参加者Session」から対象ラベル・Session IDを照合して選択します。
3. 「**登録を取り消す**」が有効な場合に押し、確認ダイアログで**取消対象とコード失効・復元不可の注意**を再確認します。違う対象なら「キャンセル」を選びます。
4. 確定後、「参加者Sessionの登録を取り消しました」と表示されたことを確認します。通常の参加者一覧から対象は消え、登録Session数にも含まれなくなります。
5. 同じ欄の「**登録取消履歴（N件）**」を開き、ラベル・Session ID・取消日時を照合します。ここには取消したSessionが残り、再発行・復元はできません。

履歴に表示するのは **ラベル、Session ID、取消日時**のみです。アクセスコード、コードのハッシュ、端末識別子、再送用の要求キーは画面に出しません。操作結果が不明なときは、同じ操作をむやみに繰り返す前に画面を再読込して**通常一覧と登録取消履歴の両方**を確認してください。

## 取消後に何が変わり、何が残るか

| 対象 | 登録取消後の扱い |
| --- | --- |
| 参加者一覧・登録人数・実施開始の対象判定 | 取消済みSessionを**除外**します。未取消の参加者Sessionはそのままです。 |
| 発行済み学習者アクセスコード | **失効**します。認証は `401 experiment_code_invalidated` となり、同じSessionへの再発行・端末登録を許可しません。 |
| 実施単位の `research.json` / `research.csv` / `research.xlsx` | 通常出力では取消済みSessionを**除外**します。11シートExcelも対象Sessionを含めません。 |
| Session・Stage・実施の登録対応・コードハッシュ | DBから物理削除せず**保持**します。コードの平文を保存・表示する機能ではありません。 |
| 取消記録・監査記録 | Session ID、取消日時、API操作の結果等をDBに**保持**します。取消記録は更新・削除できない保護を設けています。 |
| 過去にダウンロードしたJSON/CSV/Excel、端末上のデータ | **自動回収・完全消去はしません**。別途のデータ管理・保管方針が必要です。 |

これは「参加者Sessionを使用対象から外す操作」であり、研究履歴の匿名化、端末全体の消去、バックアップからの完全消去、同意撤回に伴うデータ削除を代替しません。旧研究データの確認付き削除については、履歴用資料の [研究データ管理](research-data-management.md) を参照してください。ただし旧管理画面・旧管理APIの一部は廃止済みのため、その資料に載る画面遷移を現行操作として使用しないでください。

## エラー・通信断の対処

| 画面/APIの状態 | 意味と安全な対応 |
| --- | --- |
| 「登録を取り消す」が無効 | 実施状態または一覧で分かるSession/端末/進行条件を満たしません。対象選択と状態を確認します。 |
| `400 invalid_confirmation` | 確認内容、アクセスコード世代、要求キー等が適切でありません。画面を更新して操作内容を確認します。 |
| `404 not_found` | Sessionが対象実施に属さない、取消済みで一覧から消えた、または認証・対象の確認ができません。対象と研究者権限を確認します。 |
| `409 not_eligible` | 準備中・未開始・未接続・記録なしの条件を満たしません。**DBを直接消して解決しない**でください。 |
| `409 already_withdrawn` | 別の要求で登録取消済みです。履歴を再確認します。 |
| `409 request_conflict` | 要求キーの再利用先が異なる、または競合が発生しました。一覧を更新して状態を確認します。 |
| `503 withdrawal_unavailable` / 通信断 | 確定結果が不明な可能性があります。通常一覧と取消履歴を更新して確認し、原因を調べてから再操作します。 |

サーバーは取消操作に `Idempotency-Key` を要求し、**同じキー・同じSessionで確定済みの操作**の再送は同じ取消日時を返します。別のキーで再度取り消そうとすると `409` になる場合があります。「409だから処理失敗」と決めつけず、履歴で結果を確認してください。監査記録には成功・拒否・障害の結果を記録する仕組みがありますが、保存障害がある場合まで完全な監査記録を保証するものではありません。

## 実装・検証の参照

- 研究者限定API：`POST /api/research/experiment-runs/:runId/participants/:sessionId/withdraw`。要求には `Idempotency-Key`（UUID）、`confirmed: true`、`expectedCredentialGeneration`（現在の整数世代）が必要です。UIからは自動送信します。実験用Session以外の削除に流用しません。
- 研究者向け確認：`GET /api/research/experiment-runs/:runId/participants` の `participants` は有効登録、`withdrawals` は取消履歴です。後者は上記の3項目だけです。
- 主な実装：`backend/src/experiment-session-withdrawal.ts`、`backend/src/experiment-participant-access.ts`、`frontend/src/ExperimentParticipantsPage.tsx`。
- DB保護：`backend/migrations/1791250000000_add_experiment_session_withdrawal.js`（取消記録の不変性と学習記録の存在確認）。

### 合成・隔離DBでの受け入れ確認

対象を検証した**使い捨ての模擬DB**とAPIが準備できている場合に限り、既存の総合テストに組み込まれた次の検証を実行できます。手順・環境変数は [READMEの「隔離DBと実APIの検証」](../README.md#隔離dbと実apiの検証) に従ってください。

```powershell
$env:RESEARCH_SUITE_ONLY = "test:experiment-withdrawal-acceptance"
npm run db:mock --prefix backend -- suite --name $mockName
```

`backend/src/scripts/verify-experiment-withdrawal-acceptance.ts` は、2件の合成参加者登録、確認付き取消、失効、取消履歴、JSON/CSV/11シートExcelの除外、DB上の記録保持を通して確認します。単独実行する前に `db:mock` のガード条件とAPIの起動条件を満たしてください。既存Compose DB、実研究DB、既存の `.local/`、検証JSON、画像、DBボリュームを削除・初期化しないでください。
