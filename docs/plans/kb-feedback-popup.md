## 締切と操作記録のケースの再調査

- タイムアウトした位置はP08の完了・待機画面より前の統合マップ編集画面。警告欄の高さを保持するため、失敗前から警告の要素を確保している。非表示を指定する `aria-hidden` は警告要素自身にあり、CSSがこの属性に合わせて表示を切り替える。操作記録の送信失敗が画面に通知されると属性が解除される。
- 受信した応答を確認するアサーションを加えた再実行では、両方の画面幅で503と `logSaved: false` を受信して警告が表示され、全スイートが通過した。統合マップではKB判定ダイアログを開く操作を行わないため、KB側のフォーカス復帰処理を通らない。
- 修正対象は `frontend/scripts/verify-rehearsal-ui-browser.ts`。従来のテストは送信を保留する間、同じイベントURLの要求を種類によらず失敗させ、503の受信を確認せずに警告を待っていた。失敗対象と再送の201を `STAGE_PAUSE` に限定し、503を受信した後、警告が視覚的に表示され、非表示の親要素に含まれず、ダイアログにも遮られていないことを確認する。締切表示とキャンバス位置、再送後も警告を表示する既存の検証を維持する。
- 基準コミット `5cf56ddee7e12c3be7ac21337a3f4d5394cfcaa2` の一時コピーと、修正後の作業ツリーの両方で、Edgeと合成APIを使った `npm run test:rehearsal-ui-browser` の全体実行が成功した。修正後は1366×768と1440×900で締切・警告のケースとKB練習の結果表示、修正、再判定を確認した。前回のタイムアウトは再現せず、その実行で警告が表示されなかった直接原因は未確定。比較結果とコード差分から、KBフィードバック変更による回帰を示す証拠は見つからなかった。
- フロントエンドの型検査と変更した練習ブラウザースクリプトのESLint、`git diff --check` は成功した。今回の追加変更はテストと計画書であり、実験本編のダイアログの検証には既存の成功結果を使用した。
