# ゴールマップ編集にScratch-Build UIを使う

- 基準はPR #96のマージコミット `5cf56ddee7e12c3be7ac21337a3f4d5394cfcaa2`。専用作業ツリーで実装する。
- 研究者の「ゴールマップ」一覧と新規作成から遷移する `/maps/:mapId` で、Kit未登録のゴールマップに既存のScratch-Buildエディタを表示する。Kit登録と登録済み原本の閲覧は従来の経路を使う。
- マップ種別 `GOAL` と既存の要素単位の作成・更新・削除を使う。再読込は既存のMap取得経路を使い、変更していない要素を送信し直さない。ゴールマップからKitを登録する際は、従来どおり保存済みの概念とリンクのIDを渡す。KBの照合は登録済みのKitを参照する。
- 概念の位置は既存の位置更新APIを使い、失敗時は移動先を保持して再試行できる。接続変更は保存前の始点・終点も渡して、別の更新で変更された接続を上書きしない。
- 承認されたリンク位置保存は、研究者によるKit未登録・編集中のゴールマップに限定する。要求のマップIDと、ロックしたリンクの所属マップを照合してから既存の座標列を更新する。登録済み原本は既存の編集禁止判定で拒否する。学習者マップの要求形式・ログは従来どおりとし、ゴールマップの座標更新を学習者の操作ログに追加しない。
- 位置保存に失敗した場合は保存済み位置を表示し、移動先を保持して再試行できるようにする。専用模擬DBで他マップID、無権限、Kit登録後の拒否とデータ不変を確かめ、既存の学習者リンク位置保存を回帰検証する。
- Edgeと分離した専用模擬DBで、管理画面からの作成と既存マップの編集、概念名・概念位置・接続変更の保存失敗と再試行、再読込、未編集要素と取り込み済み原本の座標の保持、Kit登録後の閲覧を確認した。既存のStage1実API回帰で研究者権限、Kit登録とKBの照合も確認した。
- リンク位置の追加検証では、Edgeで移動・保存・再読込と、503後に保持した座標での再試行を確認した。実APIで未認証は401、学習者と別マップIDは404、Kit登録済み原本は409となり、拒否後の座標が変わらないことを確認した。既存Stage1実API回帰と `test:parent-followup` が成功し、学習者の3種類のマップにおける位置保存、履歴、Undo/Redoも確認した。
- ブラウザーテストは `test:goal-map-editor-browser` として、`RESEARCH_BROWSER_CHECKS=1` の既存模擬DBスイートから実行する。既存の模擬DB検証と同じ `DATABASE_URL`、`API_BASE_URL`、`RESEARCHER_API_TOKEN` を使い、テスト開始時に識別情報とループバックを検証する。
