# 観測キューの生成元拒否と保全・復旧案

## 目的・境界
- `experiment_origin_stale` の原因とFIFO停止を切り分け、元の記録を保持した復旧契約を具体化する。今回は調査・新規隔離模擬環境の再現・設計のみ。製品コード、認可、既存DB、稼働キューを変更しない。再接続編集（別PR）の変更は含めない。
- 対象候補: [観測キュー](../../frontend/src/observation-outbox.ts)、[観測生成](../../frontend/src/learning-events.ts)、[画面登録](../../frontend/src/ExperimentLearnerPage.tsx)、[認証クライアント](../../frontend/src/auth-client.ts)、[配送表示](../../frontend/src/DeliveryStatus.tsx)、[実施の認可](../../backend/src/experiment-execution.ts)、[観測受付](../../backend/src/research-events.ts)、関連検証と既存の[配送仕様](../research-event-delivery.md)。
- 本件はブラウザー観測v1の送信停止。Map保存・再接続などのサーバー確定v2/v5とは別経路であり、本件だけでMap未保存・Map操作ログ消失と判定しない。

## 使用版・証拠の区別
- 現在のCompose起動元はmain `7afdbb0401e86324e413f55b184322aedc2727da`、Webポート5180。既存の引継ぎはPR #52版の古い作業場所・コンテナIDを指していたため、その記録だけで現在を判断しなかった。
- 対象Composeプロジェクトの現在のWeb/API/DBコンテナは読み取りでrunning/healthyを照合。Web/APIの関連ソース9件は実際のbind mountと起動元ファイルのハッシュが一致。これらの中核ソースはPR #52版から当該mainまで変更されていない。既存DBへのSQL接続・内容取得はしていない。ブラウザー内に以前ロードされたモジュール全体まで指紋照合したという意味ではない。
- ユーザー報告: 当初32件/試行済み1件。読み取り専用のIndexedDBメタデータ集計では51件/試行済み1件、生成元欠落0件、生成元6組（1/2/7/9/31/1件）、先頭の試行164回、7日超0件。これは観測時点のユーザー提供集計で、現在の全件内容やサーバー保存有無の独立照合ではない。
- 直近events POSTは409 `experiment_origin_stale`。当初の「世代一致」という回答は、その後の具体的なヘッダーメタデータで不一致と訂正された。先頭の生成元が現在より古いことを確認したが、残り50件まで旧世代とは扱わない。画面ID・Session ID・イベント本文・認証値は本資料へ転記しない。
- 再読込・端末切替・認証変更がどの時刻にどの生成元組を作ったかは未確定。試行回数やコンテナ起動時刻から推測しない。既存DBの監査確認は今回未実施。

## 現行コードで確定した構造
1. `validateExperimentRequest` は現在の本人/実施/コード/利用画面を先に検査し、events POSTの生成元画面IDと世代を現在の登録と比較する。生成元なし・不一致の両方が同じ固定コード。今回の先頭は情報欠落ではなく世代不一致による拒否と整合する。API/ネットワーク停止として再起動する問題ではない。
2. キューはorigin内のSession別に1ストリームを保持。`flush` は常に `items[0]` を試行し、当該409ではそのitemを削除・ACKせず即returnする。後続に現世代があっても試行しない。`running` のまとめはタブ内のみで、複数タブの全体的な送信許可ではない。
3. この早期returnでは拒否保留理由・最終応答を更新せず、末尾の配送報告・表示更新通知にも到達しない。itemはRETRYINGのままで、UIは「接続の回復後に再送」と表示し得る。現在の「再送待ち1」は試行済みitem数で、全件の旧世代判定や送信成功数ではない。
4. 15秒周期・online・pageshow・観測追加で再試行する。保持中でも次のflush/enqueueで7日超を自動除外し、追加時の500件/1MB超でも古いitemを除く。現在の集計は7日超0だが、タブを維持すれば無期限に保全されるとは保証しない。
5. originはenqueue実行時のグローバルな登録値から取得する。観測effectはSession/Stage/Mapを保持する一方、生成元を不変のスナップショットとして保持していない。実UIでコード切替→親のbind解除→子のcleanup観測が生成元なしで残る経路を再現した。これは予防すべき別経路だが、欠落0件の実キューの先頭原因にはしない。

### 識別子・順序を混同しない
| 値 | 意味・保持契約 |
|---|---|
| experimentOrigin.clientId / generation | 登録済み画面の生成元。画面secretや認証コードではない。既存itemの元値を修正しない |
| State.clientId / X-Client-Stream-Id | Session別の観測ストリームUUID。画面IDではなく、世代変更後も同じキューで使われる |
| item.id / Idempotency-Key | 観測の固定キー。サーバー発行eventIdとは別 |
| item.order / X-Client-Sequence | ストリーム内の元の観測順。振り直し・別ストリームへの付替えをしない |
| eventId / sequenceNumber | 保存済み受付票が指すサーバーイベントとSession保存順。クライアント順・時計と同一視しない |

## 分離環境の再現結果
- 使用版と同じクリーンな専用worktree、正規manifest/用途/nonce/loopbackガード付き新規PostgreSQL、Node 22.23.5/Windows/Playwright Edge、実APIと実IndexedDBで局所再現。稼働キュー・既存DBは使わない。Map本文・観測本文・認証値をログへ出さない。
- 生成元欠落の先頭＋現世代の後続: 先頭だけ試行して停止、両itemのキー/連番/本文/生成元の同一性を維持。ACK0、対象受付票/観測イベント0。
- 正規の研究者画面切替で旧世代の先頭＋現世代の後続: 同じ409と先頭停止。生成元を付替えず、後続は未試行。
- 模擬環境でのみ後続を先に送る反例を作成。後から小さい未保存連番を送ると409 `delivery_order_conflict`。したがって「先頭を飛ばすだけ」では回収不能な順序を確定させ得る。
- APIで保存後にブラウザーへのACKを失わせ、さらに正規画面切替を実施。同じキー/本文の受付票がDBにあるにもかかわらず、旧生成元のPOSTは受付票照合に達する前に409。同一世代の正規再送は同じ結果、異本文は `delivery_conflict` で拒否。
- 実画面のコード切替・再ログイン・正規画面承認: cleanup由来の生成元欠落が残り、新しい正常生成元の観測を塞ぐ別経路も再現。
- 対象キーを指定し、新規DBの `client_event_receipts` とv1 `research_events` を対応付けて確認。未受領側0/0、ACK喪失側1/1、逆順拒否0/0、後続成功1/1で重複なし。Mapのv5や旧ログと混同していない。
- 初回は診断fixtureの画面secret形式が既存契約を満たさず400になった。正規の32バイト形式へ修正し、期待値を変えず新しい模擬Sessionで再現を完了。失敗ログを残す。製品修正や成功するまでの無条件再試行ではない。

## 当面の保全（初回調査時点・稼働キューには未適用）
- 現タブ/同じorigin/同じプロファイルを保持し、同じSessionで学習を続けない。再読込、コード再発行、保存情報削除、DB初期化、旧世代としての強制送信、見かけ上のACKは行わない。別originでキューが空でも復旧としない。
- 実行したブラウザー診断は既存DB名を確認してからreadonlyトランザクションでメタデータだけを読む。製品のqueueStatusはreadwriteなので診断に利用しない。これまでキュー変更・再送代行・サーバー受付票照合はしていない。
- 独立バックアップは未作成。承認後、ブラウザー内だけで元のキューをローカル保全ファイルへ保存し、元のID/生成元/順序/本文を不変として件数・ダイジェストを照合する案。本文をチャット/外部へ送らず、保管場所・暗号化/アクセス制限・復元先を研究者が決める。バックアップ作成と送信成功を混同しない。

## 再発防止の具体設計（2026-11-17・全体構成は未採用、単位1の実績は末尾）

### 推奨案と守る境界
推奨は「生成時の文脈固定 → 永続保留と容量での停止 → 新しく生成する記録の画面・世代別stream → 受付票の読取照合」の段階導入。既存の混在キューを分割して送り直す方式ではない。受領未確認の旧記録は残し、現在の正規画面で将来生成する記録の配送だけを独立させる。保留を残す実施で学習を継続するかは研究者判断とし、実施全体の記録回復済みとは表示しない。

- 最新mainをリモートで読み取り確認し、作業元と同じ `7afdbb0401e86324e413f55b184322aedc2727da` と照合した。ローカルmainや稼働版は更新していない。PR #57の再接続編集は対象外。
- `item.id` は観測の冪等キー、サーバーの `eventId` は受領後の識別子。既存のいずれも再発行・改番しない。本文・元画面・元世代・created・clientTimestampも移行で変更しない。
- `client stream` は画面IDとは別の乱数UUID。`client_sequence` はそのstream内の生成順、`research_events.sequence_number` はSession内の全主体を含むサーバー保存順のまま。新stream間の発生順や遅延観測の因果関係を、どちらの連番や端末時計からも捏造しない。
- 通常POSTの本人・所属・コード世代・画面世代・実施状態・Stage/Map検査、既存の冪等性・ロック・受付票は維持。新streamを取得しても失効画面や終了済み実施からの書込みを許可しない。
- 既存記録を現在の生成元へ付け替えない。元の生成元が不明なら `ORIGIN_MISSING` として保留し、時刻・近い記録・世代番号だけから補完しない。96件の承認済みテスト破棄は履歴であり、復元・再構成も、実研究記録の自動破棄への一般化もしない。

| 案 | 旧記録・順序・受付票への影響 | 判断 |
|---|---|---|
| Session単一streamのFIFOを維持し、全体保留 | IDと連番は完全維持。先頭が未確認なら現世代も停止。全件を正規に受領照合できる場合だけ既存FIFO再開 | 移行直後の安全な既定。障害中の通常継続はできない |
| 新規生成分だけ画面・世代別stream、旧streamは保留 | 旧ID/連番は不変。新streamは新記録だけ1から採番。旧streamの未受領を解決するものではない | 推奨。配送・分析・実験継続の契約変更として別承認後に導入 |
| 旧streamの先頭を飛ばして後続送信 | 後続の受領でmaxが進み、小さい未受領連番を通常POSTへ戻せなくなる。receipt未確認をACKとも扱えない | 不採用 |
| 既存itemを世代別streamへ移送・採番し直す | 既存request_hash・一意制約・受付票と要求の対応が変わる。ACK喪失時に重複の危険 | 不採用 |
| 旧記録を封印して同じstreamの後続を送る | 元の記録は残せるが、通常APIによる遡及回収を不可逆に狭める。封印・欠測の研究判断が必要 | 代替の別契約。今回の推奨や自動処理へ含めない |

### 1. 生成元とstreamの割当
1. 画面登録が有効になった時点で、Session・画面ID・画面世代・メモリー内認証revision・登録所有者のトークンではない識別子を持つ不変の観測文脈を作る。認証コード、画面secret、Authorizationは保持キューへコピーしない。メモリー内revisionは再読込で変わり得るため、永続streamのキーそのものにはしない。
2. 将来のstream割当は `[sessionId, originClientId, originGeneration]` を名前空間とする。乱数stream UUIDはこの組と一緒に短いIndexedDB transactionで一度割当て、同じ組の再開で既存streamとnextを再利用する。画面IDが同じでも世代が異なれば新stream。コード再発行も現行コードでは画面世代を進めるが、それを本人認証の代用にはしない。旧protocolは本段階では既存単一streamのまま。
3. event生成時に文脈を引数で渡し、effectのcleanupもそのeffect開始時のSession・Stage・Map・文脈を使う。現在のglobal bindingを参照して別ユーザーの画面情報を付けない。古い文脈で生成されたcleanup観測は旧streamへ元情報のまま保持し、送信可能とは推定しない。既存の欠落itemへ元情報や新番号を補わない。将来の新規生成時に画面情報だけが欠けた場合は、確定している元Sessionの未帰属streamへ一度だけ採番して保留する案とし、画面/世代を創作しない。Session自体が確定できない場合は別Sessionへ保存せず、COMMIT未確認として停止・研究者確認へ進む。
4. bind/unbindは所有者を照合する。旧effectのunbindが新しいbindingを消さない。登録応答・イベント応答の適用時には、要求を開始した認証revision、Session、所有者、画面世代と現行状態を再比較する。不一致なら新画面へ適用・再送せず、未確認の元itemを残して後のreceipt照合へ回す。cleanupの観測を黙って抑止する方式ではない。
5. 送信時は現在の認証から `/api/me` の本人Session、登録済み画面、利用可否を確認し、同一の不変文脈のstreamだけを候補にする。実施終了・コード失効・画面切替の拒否は保留へ移し、自動再登録や再発行で迂回しない。サーバー側の検査が最終判断となる。

### 2. ブラウザー保存形式と既存記録の移行
同じ `stage1-observation-outbox` をversion 2へ上げる案。別DBを作ってv1 writerと並走させる案は、旧版が同じSessionの古いitemsを期限・容量で削除し続けるため推奨しない。

| store案 | 主キー・内容 | 更新契約 |
|---|---|---|
| 既存sessions | 既存Sessionキー・Stateをそのまま残す | 旧streamの新規採番・通常送信は凍結。receipt完全一致を確認したitemの除去とACK加算だけを明示処理で許す。行の初期化・nextの巻戻しは禁止 |
| streams | `[sessionId, streamId]`、新規生成分のitems/next/ACK/reportSequenceと固定の元画面・世代 | 新規itemのCOMMIT、試行、真正なACKでのみ更新。元のv1行からitemを移さない |
| holds | stream全体またはitemキー、固定理由、保留時刻、元descriptorのdigest、確認状態 | 本文は元storeに1部だけ保持。receiptがない記録をACK・損失へ変更しない |
| leases | `[sessionId, streamId]`、一時writer、期限、fence | 短いIDB transactionで取得・再取得・比較。認証情報は入れない |
| issues | Session・記録経路・対象操作キー等、固定理由、未解決／確認済み、確認根拠 | 観測保留と別経路のlogSaved=falseを分ける。新しい研究イベントとして挿入しない |
| control | 保存形式・移行完了・stream割当index・件数/bytes上限管理 | 元Sessionとの対応、元nextと同一性の検査を保存。認証秘密値は持たない |

- 移行前に全対象タブの新規操作と送信を止め、送信中がないことを確認する。各version 1接続が開いているとupgradeはblockedになる。現行outboxにはversionchangeで自動closeする処理がないため、旧タブを強制終了せず、未保存入力の保全を確認して利用者が閉じる計画停止が必要。新しいタブが開く競合があれば移行を進めない。旧タブを閉じると画面secretは失われるため、再開時は既存の研究者承認による正規の利用画面切替を使い、コード再発行や認可緩和で回避しない。
- versionchange transactionでstoreと保留メタデータを追加し、既存sessionsを検査する。既存State/itemsのID・本文・元情報・順序・next/ACK等は変更しない。全既存pendingを `LEGACY_REVIEW_REQUIRED` とし、同じ旧stream内で現世代に一致するitemがあっても勝手に分割・配送しない。空の旧行も再利用して番号をリセットしない。
- upgradeの失敗・中断は全体rollback。壊れた行や上限超過が見つかっても切詰め・再初期化せず、読み取れない範囲を不明として停止する。移行完了はtransaction完了と再読取の同一性検査後だけ表示する。
- upgrade完了後、旧コードの `indexedDB.open(name, 1)` はVersionErrorとなり、旧senderはこの領域へ書けない。新コードもversionchange時に新規観測/送信を止めて接続をcloseし、上位版への移行中と表示する。旧版が自動的にv2へ対応するとは説明しない。既存Sessionをそのまま学習継続させず、対応版へ統一してから再開する。旧版の閉じ際のcleanup観測は非同期COMMIT前に消失し得るため、移行前の全観測を完全保全したとは保証できない。互換版の停止境界で最終enqueue完了を確認できない場合は、その制約を研究者へ示して移行を保留する。既にCOMMIT済みのキューの保全と区別する。
- 同一origin・プロファイル内だけが対象。IP・ポート・プロファイルが異なるキューを自動発見・統合しない。ローカル保全ファイルへの退避が必要なら、研究者承認・アクセス制限・内容と件数の同一性確認を別手順で行う。退避をAPIへの受領やACKと扱わない。

### 3. 保留、順序、別タブの送信
- item状態は「通常待機／通信再試行／送信中／生成元欠落・旧世代保留／終了・失効保留／順序上の保留／受領確認済み」を区別する。`experiment_origin_stale` は記録の削除ではなく、そのstreamの自動再送停止と永続保留を一緒にCOMMITする。原因が不明な403/409等も一律に捨てず固定理由を残す。構造不正は隔離し、記録を修正して送らない。
- 旧streamの未受領が残るとき、同じstreamの後続をPOSTしない。既存receiptを読取照合すること自体は順序を進めない。受領確認済みのprefixを処理して先頭が安全に配送可能になった場合だけFIFO再開を検討する。旧streamの凍結解除には研究者の判断を要する。
- 将来生成する新streamは、旧streamを改番せず新規の1から始まる。既存DBの一意制約は `(Session,event_key)` と `(Session,stream,client_sequence)`、逆順判定はstream別maxなので、通常POSTの形式・receipt schemaを変えず表現できる。ただし実APIでの新しい分離方式の結合検証は実装後に必要。新streamへ既存itemを移した成功とは扱わない。
- streamごとに先頭1件だけを取得し、IDB transactionをHTTP待機中に開き続けない。同じキー・元本文・stream・順序で再送する。tab間のleaseとfenceは送信候補/応答適用を直列化するが、既にサーバーへ出た要求の取消や認可を保証するものではない。lease期限切れ後の別writerも同じ先頭だけを再試行し、未確認の先頭を飛ばして次を送らない。
- ACK応答の適用は、Session/stream/itemキー/要求digest/所有文脈/fenceを再照合する短いtransactionでitemの存在を確認し、除去・累計加算を一度だけ行う。二つのタブの同じ成功応答でACKを二重加算しない。遅れて届く古い所有文脈の成功は未確認のまま保留し、真正なreceipt照合で回復できるようにする。
- Session単位の全観測順をstream横断で維持した、という保証はしない。新しい分析でもclient stream内の順序とサーバー保存順を別に読む。未受領の旧観測を後日正規イベントへ挿入することは今回の案に含めず、別の回収契約・出所・遅延順・監査を決めるまで保留する。

### 4. 期限・容量・保存失敗
- 未確認記録は保留・通常待機とも期限や容量で自動削除しない。既存の7日は保留見直しの目安へ変更する案とし、超過時は `RETENTION_REVIEW_REQUIRED` へ移す。過去のexpiredLost等は保持し、新たな保留を損失として加算しない。この変更は保持期間・研究運用の承認対象。
- 有限の提案値: 元の500件/1,000,000 bytesをSessionの全streamと旧行の合計へ適用し、32Session/originを維持する。新streamごとに上限を増殖させない。補助メタデータは別に256KiB/Session、stream登録は64/Sessionを提案上限として検証する。追加値は実測と承認前の設計値であり、採用済み運用条件ではない。既存データがこの値を超えても削らず、新規受入れを止める。
- enqueue前にitems・メタデータを含む見積りをし、件数・bytes・採番を同じ短いtransactionで確定。上限やQuotaExceededError/IO失敗はtransactionを戻し、既存item/nextを保持する。QuotaExceededErrorが起きる前に必ず予測できるとは保証しない。
- まだCOMMITできていない新規観測は「ブラウザーへの保存未確認」と表示し、少量のメモリー保持で研究者の保全判断を待つ。学習を成功表示のまま無制限に続けない。次の学習操作を保留するUIは実験進行への変更なので実装前に承認する。既に確定したMap保存を勝手に取り消さず、Map保存と観測保存を分けて表示する。
- `navigator.storage.estimate()` 等は参考値に限り、空き容量・永続性の保証に使わない。HTTP LANで使えない機能やWeb Locksへ依存しない。ブラウザー/OSによる消去、端末故障、COMMIT前の終了、ユーザーによる保存領域消去は防ぎ切れない。ローカル退避・バックアップの有無も別の状態として示す。

### 5. 受付票の完全一致照合と回収の限界
候補は共通の読取照合処理を使う2経路。新規イベント受入れとは完全に分け、通常events POSTの旧生成元検査を緩めない。

- 研究者用: `POST /api/research/sessions/:id/observation-receipts/query`。既存研究者認証と対象Sessionの存在・研究者閲覧範囲を検査する。初期対象は新protocolと実施所属を確認できるSessionだけとし、R05や旧protocolへ権限を展開しない。終了済みも結果照合だけを可能とし、削除済みや権限外は固定404で存在を漏らさない。学習者からの研究者経路は既存どおり拒否する。
- 本人画面用: `POST /api/sessions/:id/observation-receipts/query` の追加案。現在有効な本人Session・画面登録・コード/画面世代・RUNNINGを通常どおり検査する。その画面が自身の過去streamを照合するだけで、旧画面の書込み権限を復活させない。終了・失効した学習者には許可せず、研究者照合と保留を残す。これは新しい読取権限/APIのため別承認後の実装単位とする。access-controlの許可リストもこの正確なパスと本人Sessionだけを追加し、他のPOST経路を一括許可しない。
- 要求: `contractVersion:1, items:[{eventKey,clientStreamId,clientSequence,requestHash}]` の閉じた形式。UUID・正の10進文字列（既存の最大15桁）・64桁hexを既存方式で検証、重複descriptor拒否。提案上限50件/16KiB。本文・認証・自由記述・生成元の推測値は受け付けない。
- requestHashは現行 `digest({event,stream,order})` のcanonical UTF-8 SHA-256そのもの。eventは元itemを変更せずPOSTと同じJSONシリアライズ後の値を用い、undefined項目を含む元オブジェクトやDBの正規化済みeventを直接hash入力にしない。orderは数値でなくヘッダーの元の10進文字列、stream等も勝手に正規化しない。ブラウザー側と既存サーバーdigestの共通テストベクトルで一致を確認するまで導入しない。JSON.stringify単独のhashを代用しない。
- SQLは対象Sessionで限定したreceiptを、event_key・client_id・client_sequence・request_hashの全一致で照合し、参照先research_eventsのSession・event_id・sequence_number・観測schemaも整合検査する。一致した保存済みeventId/sequenceNumberだけ返す。既存hashに元画面/世代が含まれないため、受付票から元の生成元の真正性を新たに証明したとは説明しない。
- 応答は各descriptorへ `MATCHED`（既存受付情報あり）、`NOT_CONFIRMED`（照合時点で確認なし）、`CONFLICT`（同一キー等の不整合）。DB障害や整合性を判定できない場合は固定503とし、NOT_CONFIRMEDへ変換しない。件数・Session・descriptorの対応と重複をクライアントで再検査する。
- `MATCHED` だけ、同じ本人画面が自身の認証済みAPI応答を受け、まだ同じitem/digestが残ることをIDB transactionで確認して受領確認へ移せる。ACK累計は一度だけ加算し、確認根拠がreceipt照合であることを保留メタデータへ残す。研究者の結果ファイルや手入力のMATCHEDだけを信頼してACKにしない。研究者と学習者は別プロファイルなので、研究者画面から他ブラウザーのキューを直接更新できるとは設計しない。
- 研究者へdescriptorを渡す必要がある場合は、内容を含まないキー/stream/順序/hashの限定ファイル等を利用者が手元で渡す案。生イベント・認証値をチャット等へ送らない。照合結果の手動表示と本人キューの正規な受領確認は別であり、終了後に本人APIへアクセスできないキューは保留のままでよい。
- NOT_CONFIRMEDは未保存確定ではない。応答喪失や並行COMMIT後に次の照合でMATCHEDになり得る。CONFLICTは自動再送・上書き禁止。未受領旧記録は元値のまま研究者判断まで保留し、通常イベントへ挿入するAPIは作らない。
- 既存receipt/research_eventsのschema変更は読取照合だけなら不要。ドメイン表へのINSERT/UPDATEとsequence消費は0件。研究者の照合アクセス・保留判断を永続監査する場合は、観測イベントと別の監査契約を事前承認する。新しい保留内訳を研究者へ永続配送する場合も、既存delivery報告の閉じた形式を勝手に広げず、別API/補助表の設計・migration承認へ分ける。

### 6. 表示と警告の解除
| 表示 | 根拠・解除条件 |
|---|---|
| 通信待ち／再試行 | 通信断・5xx・応答未確認。元要求を保持し、正規のACKまたはreceipt一致でのみ確認済みへ |
| 旧画面・世代の保留／順序上の保留 | 元情報の不一致または前方未解決。件数・理由と「現在の記録も含め全体回復済みではない」を示す。新streamの成功だけで旧保留を消さない |
| 保存領域エラー／容量で中断 | 読出不能なら過去のpending/ACKは不明。新規COMMIT失敗なら未保存と既存保持分を分ける。保全・容量解消と読取/COMMIT確認後だけ解除 |
| 受領確認済み | 正規POSTの2xx+logSaved:true+受付情報、または上記の完全一致照合。送信中やHTTP200のみを成功扱いにしない |
| 回復不能な欠損／過去の承認破棄 | 既知の消失を記録。推測で件数を増減せず、ネットワーク復旧で消さない。ユーザー承認96件破棄も別の履歴として残す |

- 配送用pendingは全streamの未確認（保留を含む）とし、「現在の送信可能待ち」「保留」「不明」を内訳表示する。既存stream別のacknowledged/reportSequenceやretryingの意味は維持し、保留件数をrejectedLostに転用しない。旧サーバーへ新しいlastResponse値を送らない。
- 観測キューの警告は、その原因となった全itemの受領確認と未解決保留/保存障害なしを確認したときだけ該当理由を解除する。一つのACKやpending 0で全理由をfalseにしない。恒久欠損は確認済みの履歴として別表示し、現在の正常配送と併記できる。
- Map/提出/Stage/回答など別経路の `logSaved=false` は、対象操作・保存経路別の未解決issueとして維持する。観測キューが空でも解除しない。既存の正規操作receiptで結果とログ保存を完全に確認できる場合だけそのissueを解決し、確認手段がない場合は研究者確認待ちとする。観測の新しいevents POSTでv2/v5を補送しない。
- 学習者の案内は「操作を止め、タブとデータを保持し、研究者へ連絡」。研究者には保留/既知欠損/不明・観測時刻・確認根拠を示す。最後の報告が古い場合や別originの情報がない場合は「現在0件・欠損なし」としない。第一段階ではローカル表示と既存の配送情報の限界を明示し、遠隔の保留内訳を取得済みとは扱わない。

### 7. 移行・ロールバック
1. 対象版・origin・プロファイル・全タブ・キュー件数と同一性を確認。研究者が継続/保全と保持上限を承認し、必要なローカル保全を行う。未保存Map操作と観測キューは別に扱う。
2. 先行互換版でwriter停止/versionchange対応を整えるか、計画停止で旧タブを閉じる。送信中0・旧接続なしでv2 upgrade。blockedなら待機して停止状態を表示し、二重DBや強制消去で回避しない。
3. 既存pendingを全体保留にして照合。新規stream送信は別の有効化判断後。新APIは先に追加しても旧POSTを変更しない。未対応APIを検出したクライアントは照合不能として保留し、POSTで代用しない。
4. v2導入前の失敗はtransaction rollbackでv1を保持。導入後はv2を読める保全対応版へアプリだけを戻し、新規生成/送信を止められるようにする。versionを1へ下げたりstore/DBを削除したりしない。新streamを旧単一streamへ戻して採番を再開しない。
5. サーバーの追加照合機能を無効化してもreceiptを削除しない。一般の認可・終了制限は戻し方に含めない。ブラウザーを消去しないと起動できない旧版への復旧は不可と明示する。

## 永続保留と容量保護の先行実装（2026-11-18）

- この段階では単一FIFOを維持する。events POSTの409かつ `experiment_origin_stale` で、現在も先頭にある同じitemだけに保留印を付ける。後続は順序上の待機として示し、その生成元を判定しない。ACKと別経路の `logSaved=false` はそれぞれの根拠で扱う。
- 同じIndexedDBをversion 2へ上げる。既存sessionsと行はupgradeで書き換えない。行に任意の先頭item IDと、新規受入れ拒否カウンターを追加する。ID、元情報、stream、連番、本文、過去の損失とACK累計を維持する。新設store、DB削除、コピー、上書き移行は不要。読み取り検査に失敗した行は初期化せず処理を止める。
- 切替前に同一origin・プロファイルの全旧版タブで操作を止め、処理中の送信と未保存入力を確認して閉じる。version 1接続が残ればupgradeはblockedとなり、新版はその間にキューを読み書きしない。blockedになったopenは既存接続解放後に中断し、新規操作・再読込・定期確認であらためてopenする。失敗または中断したupgradeはIndexedDBのtransactionで戻る。version 2以降、旧版のversion 1指定openはVersionErrorで拒否される。旧版へ戻す場合もDBを消去・降格せず、保全版での再起動または別途承認された保全手順を使う。
- 7日超は保持する。判定前に未知の旧世代を消さないよう、通常の未確認itemも期限・容量で消去しない。500件・1,000,000 bytes・32 Sessionの上限を維持し、新規受入れを拒否する。ブラウザー側の書込み失敗は新規itemと採番をrollbackし、別途表示する。研究者承認済みの削除確認経路は従来どおり。
- 同じ先頭への別タブの送信がすでに発行されている場合は取り消せない。保留が先に確定した後の古い応答で保留を解除しない。保留確定前の旧版コードによる動作、ブラウザーやOSによる消去、COMMIT前の終了までは保全できない。
- 対象はブラウザー内のoutboxと学習者表示。サーバーへの配送報告の形式と認可を維持する。世代別stream、受付票照合と旧記録回収は後続とする。
- 保留印の書込み自体が失敗した場合は、そのタブのメモリーで409を保持し、次回は印の保存だけを試す。保存が確定する前の別タブや再起動へはこの印を引き継げない。新規記録の書込み失敗通知と、Session数上限で既存行を持たない場合の受入れ拒否数もタブ内に限る。件数・bytes上限で既存行へ記録できた受入れ拒否数は再読込後も表示する。
- 保留中の元記録を配送報告でACK済み・欠損に加算しない。新規の上限拒否は既存の容量欠損フィールドで報告する。旧世代の保留内訳は学習者画面に限り、研究者画面へ届く配送報告は現行の集計形式のままとする。保留中の学習操作や記録の回収については研究者判断が残る。
