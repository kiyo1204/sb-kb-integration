# 観測キューの生成元拒否と保全・復旧案

## 目的・境界
- `experiment_origin_stale` の原因とFIFO停止を切り分け、元の記録を保持した復旧契約を具体化する。今回は調査・新規隔離模擬環境の再現・設計のみ。製品コード、認可、既存DB、稼働キューを変更しない。再接続編集（別PR）の変更は含めない。
- 対象候補: [観測キュー](../../frontend/src/observation-outbox.ts)、[観測生成](../../frontend/src/learning-events.ts)、[画面登録](../../frontend/src/ExperimentLearnerPage.tsx)、[認証クライアント](../../frontend/src/auth-client.ts)、[配送表示](../../frontend/src/DeliveryStatus.tsx)、[実施の認可](../../backend/src/experiment-execution.ts)、[観測受付](../../backend/src/research-events.ts)、関連検証と既存の[配送仕様](../research-event-delivery.md)。
- 本件はブラウザー観測v1の送信停止。Map保存・再接続などのサーバー確定v2/v5とは別経路であり、本件だけでMap未保存・Map操作ログ消失と判定しない。

## 使用版・証拠の区別
- 現在のCompose起動元はmain `7afdbb0401e86324e413f55b184322aedc2727da`、Webポート5180。既存の引継ぎはPR #52版の古い作業場所・コンテナIDを指していたため、その記録だけで現在を判断しなかった。
- 対象Composeプロジェクトの現在のWeb/API/DBコンテナは読み取りでrunning/healthyを照合。Web/APIの関連ソース9件は実際のbind mountと起動元ファイルのハッシュが一致。これらの中核ソースはPR #52版から当該mainまで変更されていない。既存DBへのSQL接続・内容取得はしていない。ブラウザー内に以前ロードされたモジュール全体まで指紋照合したという意味ではない。
- ユーザー報告: 当初32件/試行済み1件。読み取り専用のIndexedDBメタデータ集計では51件/試行済み1件、生成元欠落0件、生成元6組（1/2/7/9/31/1件）、先頭の試行164回、7日超0件。これは観測時点のユーザー提供集計で、現在の全件内容やサーバー保存有無の独立照合ではない。
- 直近events POSTは409 `experiment_origin_stale`。当初の「世代一致」という回答は、その後の具体的なヘッダーメタデータで不一致と訂正された。先頭の生成元が現在より古いことを確認したが、残り50件まで旧世代とは扱わない。画面ID・Session ID・イベント本文・認証値は本資料へ転記しない。
- 再読込・端末切替・認証変更がどの時刻にどの生成元組を作ったかは未確定。試行回数やコンテナ起動時刻から推測しない。既存DBの監査確認は今回未実施。

## 現行コードで確定した構造
1. `validateExperimentRequest` は現在の本人/実施/コード/利用画面を先に検査し、events POSTの生成元画面IDと世代を現在の登録と比較する。生成元なし・不一致の両方が同じ固定コード。今回の先頭は情報欠落ではなく世代不一致による拒否と整合する。API/ネットワーク停止として再起動する問題ではない。
2. キューはorigin内のSession別に1ストリームを保持。`flush` は常に `items[0]` を試行し、当該409ではそのitemを削除・ACKせず即returnする。後続に現世代があっても試行しない。`running` のまとめはタブ内のみで、複数タブの全体的な送信許可ではない。
3. この早期returnでは拒否保留理由・最終応答を更新せず、末尾の配送報告・表示更新通知にも到達しない。itemはRETRYINGのままで、UIは「接続の回復後に再送」と表示し得る。現在の「再送待ち1」は試行済みitem数で、全件の旧世代判定や送信成功数ではない。
4. 15秒周期・online・pageshow・観測追加で再試行する。保持中でも次のflush/enqueueで7日超を自動除外し、追加時の500件/1MB超でも古いitemを除く。現在の集計は7日超0だが、タブを維持すれば無期限に保全されるとは保証しない。
5. originはenqueue実行時のグローバルな登録値から取得する。観測effectはSession/Stage/Mapを保持する一方、生成元を不変のスナップショットとして保持していない。実UIでコード切替→親のbind解除→子のcleanup観測が生成元なしで残る経路を再現した。これは予防すべき別経路だが、欠落0件の実キューの先頭原因にはしない。

### 識別子・順序を混同しない
| 値 | 意味・保持契約 |
|---|---|
| experimentOrigin.clientId / generation | 登録済み画面の生成元。画面secretや認証コードではない。既存itemの元値を修正しない |
| State.clientId / X-Client-Stream-Id | Session別の観測ストリームUUID。画面IDではなく、世代変更後も同じキューで使われる |
| item.id / Idempotency-Key | 観測の固定キー。サーバー発行eventIdとは別 |
| item.order / X-Client-Sequence | ストリーム内の元の観測順。振り直し・別ストリームへの付替えをしない |
| eventId / sequenceNumber | 保存済み受付票が指すサーバーイベントとSession保存順。クライアント順・時計と同一視しない |

## 分離環境の再現結果
- 使用版と同じクリーンな専用worktree、正規manifest/用途/nonce/loopbackガード付き新規PostgreSQL、Node 22.23.5/Windows/Playwright Edge、実APIと実IndexedDBで局所再現。稼働キュー・既存DBは使わない。Map本文・観測本文・認証値をログへ出さない。
- 生成元欠落の先頭＋現世代の後続: 先頭だけ試行して停止、両itemのキー/連番/本文/生成元の同一性を維持。ACK0、対象受付票/観測イベント0。
- 正規の研究者画面切替で旧世代の先頭＋現世代の後続: 同じ409と先頭停止。生成元を付替えず、後続は未試行。
- 模擬環境でのみ後続を先に送る反例を作成。後から小さい未保存連番を送ると409 `delivery_order_conflict`。したがって「先頭を飛ばすだけ」では回収不能な順序を確定させ得る。
- APIで保存後にブラウザーへのACKを失わせ、さらに正規画面切替を実施。同じキー/本文の受付票がDBにあるにもかかわらず、旧生成元のPOSTは受付票照合に達する前に409。同一世代の正規再送は同じ結果、異本文は `delivery_conflict` で拒否。
- 実画面のコード切替・再ログイン・正規画面承認: cleanup由来の生成元欠落が残り、新しい正常生成元の観測を塞ぐ別経路も再現。
- 対象キーを指定し、新規DBの `client_event_receipts` とv1 `research_events` を対応付けて確認。未受領側0/0、ACK喪失側1/1、逆順拒否0/0、後続成功1/1で重複なし。Mapのv5や旧ログと混同していない。
- 初回は診断fixtureの画面secret形式が既存契約を満たさず400になった。正規の32バイト形式へ修正し、期待値を変えず新しい模擬Sessionで再現を完了。失敗ログを残す。製品修正や成功するまでの無条件再試行ではない。

## 当面の保全（初回調査時点・稼働キューには未適用）
- 現タブ/同じorigin/同じプロファイルを保持し、同じSessionで学習を続けない。再読込、コード再発行、保存情報削除、DB初期化、旧世代としての強制送信、見かけ上のACKは行わない。別originでキューが空でも復旧としない。
- 実行したブラウザー診断は既存DB名を確認してからreadonlyトランザクションでメタデータだけを読む。製品のqueueStatusはreadwriteなので診断に利用しない。これまでキュー変更・再送代行・サーバー受付票照合はしていない。
- 独立バックアップは未作成。承認後、ブラウザー内だけで元のキューをローカル保全ファイルへ保存し、元のID/生成元/順序/本文を不変として件数・ダイジェストを照合する案。本文をチャット/外部へ送らず、保管場所・暗号化/アクセス制限・復元先を研究者が決める。バックアップ作成と送信成功を混同しない。

## 再発防止の具体設計（2026-11-17・全体構成は未採用、単位1の実績は末尾）

### 推奨案と守る境界
推奨は「生成時の文脈固定 → 永続保留と容量での停止 → 新しく生成する記録の画面・世代別stream → 受付票の読取照合」の段階導入。既存の混在キューを分割して送り直す方式ではない。受領未確認の旧記録は残し、現在の正規画面で将来生成する記録の配送だけを独立させる。保留を残す実施で学習を継続するかは研究者判断とし、実施全体の記録回復済みとは表示しない。

- 最新mainをリモートで読み取り確認し、作業元と同じ `7afdbb0401e86324e413f55b184322aedc2727da` と照合した。ローカルmainや稼働版は更新していない。PR #57の再接続編集は対象外。
- `item.id` は観測の冪等キー、サーバーの `eventId` は受領後の識別子。既存のいずれも再発行・改番しない。本文・元画面・元世代・created・clientTimestampも移行で変更しない。
- `client stream` は画面IDとは別の乱数UUID。`client_sequence` はそのstream内の生成順、`research_events.sequence_number` はSession内の全主体を含むサーバー保存順のまま。新stream間の発生順や遅延観測の因果関係を、どちらの連番や端末時計からも捏造しない。
- 通常POSTの本人・所属・コード世代・画面世代・実施状態・Stage/Map検査、既存の冪等性・ロック・受付票は維持。新streamを取得しても失効画面や終了済み実施からの書込みを許可しない。
- 既存記録を現在の生成元へ付け替えない。元の生成元が不明なら `ORIGIN_MISSING` として保留し、時刻・近い記録・世代番号だけから補完しない。96件の承認済みテスト破棄は履歴であり、復元・再構成も、実研究記録の自動破棄への一般化もしない。

| 案 | 旧記録・順序・受付票への影響 | 判断 |
|---|---|---|
| Session単一streamのFIFOを維持し、全体保留 | IDと連番は完全維持。先頭が未確認なら現世代も停止。全件を正規に受領照合できる場合だけ既存FIFO再開 | 移行直後の安全な既定。障害中の通常継続はできない |
| 新規生成分だけ画面・世代別stream、旧streamは保留 | 旧ID/連番は不変。新streamは新記録だけ1から採番。旧streamの未受領を解決するものではない | 推奨。配送・分析・実験継続の契約変更として別承認後に導入 |
| 旧streamの先頭を飛ばして後続送信 | 後続の受領でmaxが進み、小さい未受領連番を通常POSTへ戻せなくなる。receipt未確認をACKとも扱えない | 不採用 |
| 既存itemを世代別streamへ移送・採番し直す | 既存request_hash・一意制約・受付票と要求の対応が変わる。ACK喪失時に重複の危険 | 不採用 |
| 旧記録を封印して同じstreamの後続を送る | 元の記録は残せるが、通常APIによる遡及回収を不可逆に狭める。封印・欠測の研究判断が必要 | 代替の別契約。今回の推奨や自動処理へ含めない |

### 1. 生成元とstreamの割当
1. 画面登録が有効になった時点で、Session・画面ID・画面世代・メモリー内認証revision・登録所有者のトークンではない識別子を持つ不変の観測文脈を作る。認証コード、画面secret、Authorizationは保持キューへコピーしない。メモリー内revisionは再読込で変わり得るため、永続streamのキーそのものにはしない。
2. 将来のstream割当は `[sessionId, originClientId, originGeneration]` を名前空間とする。乱数stream UUIDはこの組と一緒に短いIndexedDB transactionで一度割当て、同じ組の再開で既存streamとnextを再利用する。画面IDが同じでも世代が異なれば新stream。コード再発行も現行コードでは画面世代を進めるが、それを本人認証の代用にはしない。旧protocolは本段階では既存単一streamのまま。
3. event生成時に文脈を引数で渡し、effectのcleanupもそのeffect開始時のSession・Stage・Map・文脈を使う。現在のglobal bindingを参照して別ユーザーの画面情報を付けない。古い文脈で生成されたcleanup観測は旧streamへ元情報のまま保持し、送信可能とは推定しない。既存の欠落itemへ元情報や新番号を補わない。将来の新規生成時に画面情報だけが欠けた場合は、確定している元Sessionの未帰属streamへ一度だけ採番して保留する案とし、画面/世代を創作しない。Session自体が確定できない場合は別Sessionへ保存せず、COMMIT未確認として停止・研究者確認へ進む。
4. bind/unbindは所有者を照合する。旧effectのunbindが新しいbindingを消さない。登録応答・イベント応答の適用時には、要求を開始した認証revision、Session、所有者、画面世代と現行状態を再比較する。不一致なら新画面へ適用・再送せず、未確認の元itemを残して後のreceipt照合へ回す。cleanupの観測を黙って抑止する方式ではない。
5. 送信時は現在の認証から `/api/me` の本人Session、登録済み画面、利用可否を確認し、同一の不変文脈のstreamだけを候補にする。実施終了・コード失効・画面切替の拒否は保留へ移し、自動再登録や再発行で迂回しない。サーバー側の検査が最終判断となる。

### 2. ブラウザー保存形式と既存記録の移行
同じ `stage1-observation-outbox` をversion 2へ上げる案。別DBを作ってv1 writerと並走させる案は、旧版が同じSessionの古いitemsを期限・容量で削除し続けるため推奨しない。

| store案 | 主キー・内容 | 更新契約 |
|---|---|---|
| 既存sessions | 既存Sessionキー・Stateをそのまま残す | 旧streamの新規採番・通常送信は凍結。receipt完全一致を確認したitemの除去とACK加算だけを明示処理で許す。行の初期化・nextの巻戻しは禁止 |
| streams | `[sessionId, streamId]`、新規生成分のitems/next/ACK/reportSequenceと固定の元画面・世代 | 新規itemのCOMMIT、試行、真正なACKでのみ更新。元のv1行からitemを移さない |
| holds | stream全体またはitemキー、固定理由、保留時刻、元descriptorのdigest、確認状態 | 本文は元storeに1部だけ保持。receiptがない記録をACK・損失へ変更しない |
| leases | `[sessionId, streamId]`、一時writer、期限、fence | 短いIDB transactionで取得・再取得・比較。認証情報は入れない |
| issues | Session・記録経路・対象操作キー等、固定理由、未解決／確認済み、確認根拠 | 観測保留と別経路のlogSaved=falseを分ける。新しい研究イベントとして挿入しない |
| control | 保存形式・移行完了・stream割当index・件数/bytes上限管理 | 元Sessionとの対応、元nextと同一性の検査を保存。認証秘密値は持たない |

- 移行前に全対象タブの新規操作と送信を止め、送信中がないことを確認する。各version 1接続が開いているとupgradeはblockedになる。現行outboxにはversionchangeで自動closeする処理がないため、旧タブを強制終了せず、未保存入力の保全を確認して利用者が閉じる計画停止が必要。新しいタブが開く競合があれば移行を進めない。旧タブを閉じると画面secretは失われるため、再開時は既存の研究者承認による正規の利用画面切替を使い、コード再発行や認可緩和で回避しない。
- versionchange transactionでstoreと保留メタデータを追加し、既存sessionsを検査する。既存State/itemsのID・本文・元情報・順序・next/ACK等は変更しない。全既存pendingを `LEGACY_REVIEW_REQUIRED` とし、同じ旧stream内で現世代に一致するitemがあっても勝手に分割・配送しない。空の旧行も再利用して番号をリセットしない。
- upgradeの失敗・中断は全体rollback。壊れた行や上限超過が見つかっても切詰め・再初期化せず、読み取れない範囲を不明として停止する。移行完了はtransaction完了と再読取の同一性検査後だけ表示する。
- upgrade完了後、旧コードの `indexedDB.open(name, 1)` はVersionErrorとなり、旧senderはこの領域へ書けない。新コードもversionchange時に新規観測/送信を止めて接続をcloseし、上位版への移行中と表示する。旧版が自動的にv2へ対応するとは説明しない。既存Sessionをそのまま学習継続させず、対応版へ統一してから再開する。旧版の閉じ際のcleanup観測は非同期COMMIT前に消失し得るため、移行前の全観測を完全保全したとは保証できない。互換版の停止境界で最終enqueue完了を確認できない場合は、その制約を研究者へ示して移行を保留する。既にCOMMIT済みのキューの保全と区別する。
- 同一origin・プロファイル内だけが対象。IP・ポート・プロファイルが異なるキューを自動発見・統合しない。ローカル保全ファイルへの退避が必要なら、研究者承認・アクセス制限・内容と件数の同一性確認を別手順で行う。退避をAPIへの受領やACKと扱わない。

### 3. 保留、順序、別タブの送信
- item状態は「通常待機／通信再試行／送信中／生成元欠落・旧世代保留／終了・失効保留／順序上の保留／受領確認済み」を区別する。`experiment_origin_stale` は記録の削除ではなく、そのstreamの自動再送停止と永続保留を一緒にCOMMITする。原因が不明な403/409等も一律に捨てず固定理由を残す。構造不正は隔離し、記録を修正して送らない。
- 旧streamの未受領が残るとき、同じstreamの後続をPOSTしない。既存receiptを読取照合すること自体は順序を進めない。受領確認済みのprefixを処理して先頭が安全に配送可能になった場合だけFIFO再開を検討する。旧streamの凍結解除には研究者の判断を要する。
- 将来生成する新streamは、旧streamを改番せず新規の1から始まる。既存DBの一意制約は `(Session,event_key)` と `(Session,stream,client_sequence)`、逆順判定はstream別maxなので、通常POSTの形式・receipt schemaを変えず表現できる。ただし実APIでの新しい分離方式の結合検証は実装後に必要。新streamへ既存itemを移した成功とは扱わない。
- streamごとに先頭1件だけを取得し、IDB transactionをHTTP待機中に開き続けない。同じキー・元本文・stream・順序で再送する。tab間のleaseとfenceは送信候補/応答適用を直列化するが、既にサーバーへ出た要求の取消や認可を保証するものではない。lease期限切れ後の別writerも同じ先頭だけを再試行し、未確認の先頭を飛ばして次を送らない。
- ACK応答の適用は、Session/stream/itemキー/要求digest/所有文脈/fenceを再照合する短いtransactionでitemの存在を確認し、除去・累計加算を一度だけ行う。二つのタブの同じ成功応答でACKを二重加算しない。遅れて届く古い所有文脈の成功は未確認のまま保留し、真正なreceipt照合で回復できるようにする。
- Session単位の全観測順をstream横断で維持した、という保証はしない。新しい分析でもclient stream内の順序とサーバー保存順を別に読む。未受領の旧観測を後日正規イベントへ挿入することは今回の案に含めず、別の回収契約・出所・遅延順・監査を決めるまで保留する。

### 4. 期限・容量・保存失敗
- 未確認記録は保留・通常待機とも期限や容量で自動削除しない。既存の7日は保留見直しの目安へ変更する案とし、超過時は `RETENTION_REVIEW_REQUIRED` へ移す。過去のexpiredLost等は保持し、新たな保留を損失として加算しない。この変更は保持期間・研究運用の承認対象。
- 有限の提案値: 元の500件/1,000,000 bytesをSessionの全streamと旧行の合計へ適用し、32Session/originを維持する。新streamごとに上限を増殖させない。補助メタデータは別に256KiB/Session、stream登録は64/Sessionを提案上限として検証する。追加値は実測と承認前の設計値であり、採用済み運用条件ではない。既存データがこの値を超えても削らず、新規受入れを止める。
- enqueue前にitems・メタデータを含む見積りをし、件数・bytes・採番を同じ短いtransactionで確定。上限やQuotaExceededError/IO失敗はtransactionを戻し、既存item/nextを保持する。QuotaExceededErrorが起きる前に必ず予測できるとは保証しない。
- まだCOMMITできていない新規観測は「ブラウザーへの保存未確認」と表示し、少量のメモリー保持で研究者の保全判断を待つ。学習を成功表示のまま無制限に続けない。次の学習操作を保留するUIは実験進行への変更なので実装前に承認する。既に確定したMap保存を勝手に取り消さず、Map保存と観測保存を分けて表示する。
- `navigator.storage.estimate()` 等は参考値に限り、空き容量・永続性の保証に使わない。HTTP LANで使えない機能やWeb Locksへ依存しない。ブラウザー/OSによる消去、端末故障、COMMIT前の終了、ユーザーによる保存領域消去は防ぎ切れない。ローカル退避・バックアップの有無も別の状態として示す。

### 5. 受付票の完全一致照合と回収の限界
読取り専用APIの初回実装は、末尾の「単位4a」の契約を推奨する。以下の研究者経路・キューへの反映は後続の検討案。

候補は共通の読取照合処理を使う2経路。新規イベント受入れとは完全に分け、通常events POSTの旧生成元検査を緩めない。

- 研究者用: `POST /api/research/sessions/:id/observation-receipts/query`。既存研究者認証と対象Sessionの存在・研究者閲覧範囲を検査する。初期対象は新protocolと実施所属を確認できるSessionだけとし、R05や旧protocolへ権限を展開しない。終了済みも結果照合だけを可能とし、削除済みや権限外は固定404で存在を漏らさない。学習者からの研究者経路は既存どおり拒否する。
- 本人画面用: `POST /api/sessions/:id/observation-receipts/query` の追加案。現在有効な本人Session・画面登録・コード/画面世代・RUNNINGを通常どおり検査する。その画面が自身の過去streamを照合するだけで、旧画面の書込み権限を復活させない。終了・失効した学習者には許可せず、研究者照合と保留を残す。これは新しい読取権限/APIのため別承認後の実装単位とする。access-controlの許可リストもこの正確なパスと本人Sessionだけを追加し、他のPOST経路を一括許可しない。
- 要求: `contractVersion:1, items:[{eventKey,clientStreamId,clientSequence,requestHash}]` の閉じた形式。UUID・正の10進文字列（既存の最大15桁）・64桁hexを既存方式で検証、重複descriptor拒否。提案上限50件/16KiB。本文・認証・自由記述・生成元の推測値は受け付けない。
- requestHashは現行 `digest({event,stream,order})` のcanonical UTF-8 SHA-256そのもの。eventは元itemを変更せずPOSTと同じJSONシリアライズ後の値を用い、undefined項目を含む元オブジェクトやDBの正規化済みeventを直接hash入力にしない。orderは数値でなくヘッダーの元の10進文字列、stream等も勝手に正規化しない。ブラウザー側と既存サーバーdigestの共通テストベクトルで一致を確認するまで導入しない。JSON.stringify単独のhashを代用しない。
- SQLは対象Sessionで限定したreceiptを、event_key・client_id・client_sequence・request_hashの全一致で照合し、参照先research_eventsのSession・event_id・sequence_number・観測schemaも整合検査する。一致した保存済みeventId/sequenceNumberだけ返す。既存hashに元画面/世代が含まれないため、受付票から元の生成元の真正性を新たに証明したとは説明しない。
- 応答は各descriptorへ `MATCHED`（既存受付情報あり）、`NOT_CONFIRMED`（照合時点で確認なし）、`CONFLICT`（同一キー等の不整合）。DB障害や整合性を判定できない場合は固定503とし、NOT_CONFIRMEDへ変換しない。件数・Session・descriptorの対応と重複をクライアントで再検査する。
- `MATCHED` だけ、同じ本人画面が自身の認証済みAPI応答を受け、まだ同じitem/digestが残ることをIDB transactionで確認して受領確認へ移せる。ACK累計は一度だけ加算し、確認根拠がreceipt照合であることを保留メタデータへ残す。研究者の結果ファイルや手入力のMATCHEDだけを信頼してACKにしない。研究者と学習者は別プロファイルなので、研究者画面から他ブラウザーのキューを直接更新できるとは設計しない。
- 研究者へdescriptorを渡す必要がある場合は、内容を含まないキー/stream/順序/hashの限定ファイル等を利用者が手元で渡す案。生イベント・認証値をチャット等へ送らない。照合結果の手動表示と本人キューの正規な受領確認は別であり、終了後に本人APIへアクセスできないキューは保留のままでよい。
- NOT_CONFIRMEDは未保存確定ではない。応答喪失や並行COMMIT後に次の照合でMATCHEDになり得る。CONFLICTは自動再送・上書き禁止。未受領旧記録は元値のまま研究者判断まで保留し、通常イベントへ挿入するAPIは作らない。
- 既存receipt/research_eventsのschema変更は読取照合だけなら不要。ドメイン表へのINSERT/UPDATEとsequence消費は0件。研究者の照合アクセス・保留判断を永続監査する場合は、観測イベントと別の監査契約を事前承認する。新しい保留内訳を研究者へ永続配送する場合も、既存delivery報告の閉じた形式を勝手に広げず、別API/補助表の設計・migration承認へ分ける。

### 6. 表示と警告の解除
| 表示 | 根拠・解除条件 |
|---|---|
| 通信待ち／再試行 | 通信断・5xx・応答未確認。元要求を保持し、正規のACKまたはreceipt一致でのみ確認済みへ |
| 旧画面・世代の保留／順序上の保留 | 元情報の不一致または前方未解決。件数・理由と「現在の記録も含め全体回復済みではない」を示す。新streamの成功だけで旧保留を消さない |
| 保存領域エラー／容量で中断 | 読出不能なら過去のpending/ACKは不明。新規COMMIT失敗なら未保存と既存保持分を分ける。保全・容量解消と読取/COMMIT確認後だけ解除 |
| 受領確認済み | 正規POSTの2xx+logSaved:true+受付情報、または上記の完全一致照合。送信中やHTTP200のみを成功扱いにしない |
| 回復不能な欠損／過去の承認破棄 | 既知の消失を記録。推測で件数を増減せず、ネットワーク復旧で消さない。ユーザー承認96件破棄も別の履歴として残す |

- 配送用pendingは全streamの未確認（保留を含む）とし、「現在の送信可能待ち」「保留」「不明」を内訳表示する。既存stream別のacknowledged/reportSequenceやretryingの意味は維持し、保留件数をrejectedLostに転用しない。旧サーバーへ新しいlastResponse値を送らない。
- 観測キューの警告は、その原因となった全itemの受領確認と未解決保留/保存障害なしを確認したときだけ該当理由を解除する。一つのACKやpending 0で全理由をfalseにしない。恒久欠損は確認済みの履歴として別表示し、現在の正常配送と併記できる。
- Map/提出/Stage/回答など別経路の `logSaved=false` は、対象操作・保存経路別の未解決issueとして維持する。観測キューが空でも解除しない。既存の正規操作receiptで結果とログ保存を完全に確認できる場合だけそのissueを解決し、確認手段がない場合は研究者確認待ちとする。観測の新しいevents POSTでv2/v5を補送しない。
- 学習者の案内は「操作を止め、タブとデータを保持し、研究者へ連絡」。研究者には保留/既知欠損/不明・観測時刻・確認根拠を示す。最後の報告が古い場合や別originの情報がない場合は「現在0件・欠損なし」としない。第一段階ではローカル表示と既存の配送情報の限界を明示し、遠隔の保留内訳を取得済みとは扱わない。

### 7. 移行・ロールバック
1. 対象版・origin・プロファイル・全タブ・キュー件数と同一性を確認。研究者が継続/保全と保持上限を承認し、必要なローカル保全を行う。未保存Map操作と観測キューは別に扱う。
2. 先行互換版でwriter停止/versionchange対応を整えるか、計画停止で旧タブを閉じる。送信中0・旧接続なしでv2 upgrade。blockedなら待機して停止状態を表示し、二重DBや強制消去で回避しない。
3. 既存pendingを全体保留にして照合。新規stream送信は別の有効化判断後。新APIは先に追加しても旧POSTを変更しない。未対応APIを検出したクライアントは照合不能として保留し、POSTで代用しない。
4. v2導入前の失敗はtransaction rollbackでv1を保持。導入後はv2を読める保全対応版へアプリだけを戻し、新規生成/送信を止められるようにする。versionを1へ下げたりstore/DBを削除したりしない。新streamを旧単一streamへ戻して採番を再開しない。
5. サーバーの追加照合機能を無効化してもreceiptを削除しない。一般の認可・終了制限は戻し方に含めない。ブラウザーを消去しないと起動できない旧版への復旧は不可と明示する。

## 永続保留と容量保護の先行実装（2026-11-18）

- この段階では単一FIFOを維持する。events POSTの409かつ `experiment_origin_stale` で、現在も先頭にある同じitemだけに保留印を付ける。後続は順序上の待機として示し、その生成元を判定しない。ACKと別経路の `logSaved=false` はそれぞれの根拠で扱う。
- 同じIndexedDBをversion 2へ上げる。既存sessionsと行はupgradeで書き換えない。行に任意の先頭item IDと、新規受入れ拒否カウンターを追加する。ID、元情報、stream、連番、本文、過去の損失とACK累計を維持する。新設store、DB削除、コピー、上書き移行は不要。読み取り検査に失敗した行は初期化せず処理を止める。
- 切替前に同一origin・プロファイルの全旧版タブで操作を止め、処理中の送信と未保存入力を確認して閉じる。version 1接続が残ればupgradeはblockedとなり、新版はその間にキューを読み書きしない。blockedになったopenは既存接続解放後に中断し、新規操作・再読込・定期確認であらためてopenする。失敗または中断したupgradeはIndexedDBのtransactionで戻る。version 2以降、旧版のversion 1指定openはVersionErrorで拒否される。旧版へ戻す場合もDBを消去・降格せず、保全版での再起動または別途承認された保全手順を使う。
- 7日超は保持する。判定前に未知の旧世代を消さないよう、通常の未確認itemも期限・容量で消去しない。500件・1,000,000 bytes・32 Sessionの上限を維持し、新規受入れを拒否する。ブラウザー側の書込み失敗は新規itemと採番をrollbackし、別途表示する。研究者承認済みの削除確認経路は従来どおり。
- 同じ先頭への別タブの送信がすでに発行されている場合は取り消せない。保留が先に確定した後の古い応答で保留を解除しない。保留確定前の旧版コードによる動作、ブラウザーやOSによる消去、COMMIT前の終了までは保全できない。
- 対象はブラウザー内のoutboxと学習者表示。サーバーへの配送報告の形式と認可を維持する。世代別stream、受付票照合と旧記録回収は後続とする。
- 保留印の書込み自体が失敗した場合は、そのタブのメモリーで409を保持し、次回は印の保存だけを試す。保存が確定する前の別タブや再起動へはこの印を引き継げない。新規記録の書込み失敗通知と、Session数上限で既存行を持たない場合の受入れ拒否数もタブ内に限る。件数・bytes上限で既存行へ記録できた受入れ拒否数は再読込後も表示する。
- 保留中の元記録を配送報告でACK済み・欠損に加算しない。新規の上限拒否は既存の容量欠損フィールドで報告する。旧世代の保留内訳は学習者画面に限り、研究者画面へ届く配送報告は現行の集計形式のままとする。保留中の学習操作や記録の回収については研究者判断が残る。

## 世代別streamの実装条件（2026-11-18・設計確定）

起点はPR #59統合版 `aaab16e163ef9dc941d2a0430ece8e375928acbf`。同一Gitツリー `049837c7614884803707509265f01e555d3d1755` の作業先で確認した。本節は上記の先行設計のうち、実装済みのv2からの移行、割当・送信の開始条件、保全版の条件を具体化する。対象は新protocol `SBKB_INTEGRATION_V1` の学習者観測キュー。Map・Stage・FBの操作結果など別経路の受領仕様と研究イベントの意味は維持する。

### 既存データと新規生成の境界

- 同じIndexedDBをv2からv3へ上げ、`sessions` の行はキー、ID、生成元、stream、連番、本文、採番位置、ACKや既知の損失、保留印を含め、そのまま保持する。新protocolの既存行は旧streamとして参照し、新規採番・送信を凍結する。先頭が旧世代なら後続に現世代の記録があっても、同じstreamから抜き出さない。既存混在行の未確認記録全体を「旧キューの未確認」とし、409を確認済みの先頭と順序待ちを内訳で区別する。旧protocolはv3対応コードから従来の行・単一streamで扱う。移行時点で所属やprotocolを推測して行を書き換えない。
- 有効化は計画停止後かつ研究者が旧キューの保留と実験継続を確認した状態で行う。初期状態は停止とし、enqueueと送信権取得では同じ永続設定を各書込み取引で読む。停止へ戻した後は新たな取得を止め、到達済み要求は未確認の先頭として扱えるよう残す。対象の操作発生時に確定していたSession、登録済みの画面ID、画面世代を用いる。新規生成を許可した後の最初のenqueueで、`[sessionId, originClientId, originGeneration]` に乱数stream UUIDを1本割り当て、記録のCOMMITと同時に1から採番する。登録時に空streamを量産しない。同じオリジン・プロファイル内の同じ組は再読込・再起動後も同じstreamと次の番号を使う。研究者の正規画面切替でIDまたは世代が変わった後の新規記録には別streamを使う。起動や再読込だけを理由に世代を進めない。認証revision・画面所有者は処理の有効性確認に使い、永続キーへ入れない。アクセスコード・画面secretは保存しない。
- 切替直前に捕捉済みのcleanup等は、元の文脈を保存する。元画面のstreamへ保持し、元画面が現行でなければ送信対象から外す。元のstreamが未作成なら、同じ組の正規記録として上限内で採番・保留できる設計にする。生成元が欠落した新protocol記録は、今回の実装単位では既存の「保持できなかった」通知に従い、新streamや現世代を推測しない。未帰属streamの追加は別の判断とする。既存行の欠落は補完しない。

### 連番・受付票・認可

- 既存 `POST /api/sessions/:sessionId/events` を使用する。`research-events.ts` は `(Session,event_key)` で既存受付票を探し、同じ `digest({event,stream,order})` なら同じ201・`eventId`・`sequenceNumber`・`logSaved:true` を返す。同じキーで本文・stream・連番のいずれかが違えば409 `delivery_conflict`。受付票の主キーはSessionとイベントキー、もう一つの一意制約はSession・stream・クライアント連番。新規保存の取引ではキーとstreamを順にロックし、受付票を再確認してからstream別の `max(client_sequence)` 以下を409 `delivery_order_conflict` とする。イベントと受付票は同じ取引で確定する。このためAのmaxが100でも新stream Bの1は比較対象に含まれない。APIは欠番のない連続増加までは検査しないため、ブラウザーが先頭の確定前に2以降を送らない。
- `/api/me` は本人Session・公開条件・終了の確認に使えるが、画面登録やRUNNINGの証明にはならない。送信候補は既存の正規登録に成功した現行のローカル文脈と完全に一致するstreamだけに絞る。POSTごとに既存の本人・所属・コード世代・画面認証・画面世代・生成元・実施状態・Stage/Mapのサーバー検査を通す。生成元検査はルートの受付票検索より先に実行される。新規保存の取引内でも画面認証・世代・状態を再検査する。早期受付票再生は最初の検査と別処理なので、画面切替と競合した成功応答が遅れて届き得るが、その経路で新しいイベントは作られない。境界をまたいだ応答はクライアントが照合して適用しない。新たな認可条件や旧生成元向けの再生経路は追加しない。
- ACK応答喪失や通信断では同じ先頭のID・元本文・stream・連番・生成元で再試行する。元画面の認可がまだ有効なら受付票の201を再取得可能。認可失効後や生成元拒否後は未確認のまま保留し、サーバーに保存済みかどうかを推測しない。`experiment_origin_stale`、画面失効、実施終了、連番・内容競合、その他の判断できない拒否で新streamの該当先頭を自動削除・飛越ししない。通信断・5xx・確認不能な成功応答は再試行待ち。疑わしいreceiptやACKは付け替えない。
- `client_sequence` はそのstream内のみ、サーバーの `sequenceNumber` はSession内の保存順。旧世代の受付が後から確定する場合を含め、stream横断の操作発生順や欠損の解消を保証しない。`Idempotency-Key` を別streamで再利用しない。既存サーバーではPOST本文・ヘッダー、受付票・DBのschema変更は不要と判断した。実装時は分離した実APIで両streamの受付票とサーバー順を照合する。

### タブ間排他、再起動、容量

- v3では `streams` を画面・世代の複合キーで管理し、同一Sessionのstream UUIDに一意性を持たせる。`control` で有効化状態と集約容量を管理する。割当・採番・本文・容量予約を一つの短いIndexedDB書込み取引でCOMMITする。既存 `sessions` と新streamの保留・送信待ちを合算して500件・1,000,000 bytes/Session、32 Session/originを適用する。補助メタデータは先行案の64 stream・256 KiB/Sessionを受入試験の仮上限とし、実機計測と研究者承認で決定する。空になったstreamの採番位置も保持する。上限・書込み失敗時は既存記録と採番位置を保ち、新規分の保持失敗を明示する。旧記録の容量を空けるための自動削除や、番号上限を回避するためのリセット・同世代stream新設は行わない。
- `leases` はstreamごとにタブの一時ID、期限、単調増加するfenceを持つ。先頭の確保とfence更新を同じ取引に収め、HTTP応答を待つ間は取引を閉じる。期限切れ・再起動・タブ停止後は同じ先頭から再開する。期限切れで実際の送信が重複し得るので、保存の重複は同じ冪等キーを用いるAPIで防ぐ。ローカルACKの反映は、送信時の認証revision・画面所有者と現在を確認し、stream・先頭ID・連番・生成元・本文指紋・fenceが一致する短い取引内で除去と累計加算を一度だけ行う。到達済みHTTPの取消は前提にしない。
- v3を開くときは、全タブの停止と未保存入力・送信中処理の確認を運用上の必須条件とする。PR #59のv2タブはversionchangeで自動的にDB接続を閉じるため、`blocked` が出なかったことは旧タブや旧要求がない証拠にならない。対応版は停止通知を出し、送信・enqueueを開始せず、確定済みの旧行と新streamの読取り結果を照合できた段階で移行完了を示す。upgrade中断は取引全体を戻す。v3確定後の復帰先は**v3を読める保全専用版**。PR #59のv2対応保全版もv3は読めない。復帰時は同じオリジン・プロファイルで書込み・送信を止め、v3行を照合する。保全専用版でも読めなければ配信停止とキュー保全を継続する。

- 送信の前後で本人Session・画面ID・生成元世代と、メモリー上の認証および画面登録のrevisionを照合する。POSTは既存の `apiFetch` とサーバー認可を通る。IndexedDBでstreamの先頭に送信権とfenceを付け、HTTPはトランザクションの外で実行する。受付確認済みにするのは、成功応答の `logSaved:true`・イベントID・サーバー連番がそろい、応答時に認証・送信権・同一先頭を再確認できた場合のみ。先頭を外す処理とACK累計の更新を同時に確定する。応答不明・通信断では同じキー・stream・番号・本文を残す。401は認証確認待ち、旧画面の409と実施終了は保留とする。
- 保留中のv2行と現行以外のv3行の未確認件数は「旧記録の保留」に表示し、現行streamの未確認数、受付確認数、送信状態とは別に扱う。別操作の `logSaved=false` に対応する警告は現行streamのACK後も維持する。v3の送信結果はstream行に追記する。復帰時に使用する読取専用版はこの送信結果を理解する単位3b以後のものを保持し、v2専用版や単位3aだけの読取版へ戻さない。
- 実API検証は、Node.js 22.23.5／Windows／Edge 157系と、既存migrationだけを適用した識別済みの新規使い捨てPostgreSQLで実施。合成セッションを新規作成し、旧streamに実受付票1・2とブラウザーの保留2件を用意した。現行streamの1をDB保存後にブラウザーへの応答を遮断した。再起動後の再送は同じキー・本文・stream・連番で同じ201と受付情報を返した。再送応答待ちの間は別タブからの送信が進まず、1のACK後に2が送信された。旧v2行の内容は全項目一致し、そこからの送信は0件。

- 再現コマンドは既存のDBガードを通る `npm run db:mock --prefix backend -- verify-v3-stream --name <今回専用の模擬DB名>`。初回は検証ページのReact DOM読み込みで中断し、読込み設定を修正して新規合成セッションで実行した。実APIの対象検証と単位3aの保存・移行・保全回帰、前後端の型検査・build・対象Lint、差分チェックを実施した。通常ビルドはPR #59のJS・CSS・HTMLのSHA-256がすべて一致。従来のchunkサイズ警告は残る。期限切れの送信権を引き継ぐ際の競合や、端末異常終了からの復旧は実機試験に残す。
- API、認可、サーバーDBの契約は変更していない。受付票照合API、旧記録回収、通常画面からの有効化・配信は後続工程。PR #59の配信判断は参加者端末での確認待ち。

### 送信権の期限切れとタブ終了の受入（2026-11-18）

- 専用の新規Edgeプロファイルと、識別マーカーで分離を確認した新規の使い捨てPostgreSQLを使用。既存の実API・受付票照合を再利用し、送信権に関わる4ケースだけを実行した。検証コマンドは `npm run db:mock --prefix backend -- verify-v3-lease --name <今回専用の模擬DB名>`。送信前はブラウザーのfetch入口、保存後は実API応答の転送前で処理を保留した。タブ終了は解放処理を完走させずタブを閉じる方法で模擬した。引継ぎ側だけの時計を、IndexedDBに保存された期限の直前・直後へ設定し、期限までの実時間を待たずに確認した。
- **送信前の終了。** 先頭の送信権が確定し、ネットワーク要求0件の状態で送信元タブを閉じた。引継ぎ先は期限前にPOSTせず、期限後に同じ先頭を送った。先頭のACK後にだけ次の連番が送られた。

- **送信中の期限切れ。** 旧タブと引継ぎ先の同じ先頭に対する201を両方保留した。新しい送信権の確定後、先に旧タブの応答を渡しても、引継ぎ先の送信権・先頭・次の記録・ACK累計・送信中表示は一致した。引継ぎ先の応答を渡してからACKと後続送信が進んだ。
- **引継ぎ前後の画面・世代切替。** 正規の画面切替が先の場合、新しい画面は旧streamを選ばず、切替を知らない旧タブの要求は `409 experiment_client_stale` となった。引継ぎが先の場合は、旧画面に対する2つの201を保留して正規切替を行い、応答を渡しても旧streamの2件は未確認で残り、新画面のACKは増えなかった。新画面の新規streamは1から送れた。保存済みでも応答を適用できなかった記録は未確認のままとした。
- 新規のDBイベント8件と受付票8件を照合。各記録1件で重複0、拒否・未送信の記録への受付票追加0、ACKを確認できない記録の削除・ACK化0。旧v2の保留2件はID・生成元・stream・連番・本文・保留印を含む行全体が一致した。終了後、今回の模擬DBは識別情報と接続残数0を確認して片付けた。

## 単位4a 旧世代の観測記録と受付票の読取り照合

基準はPR #60統合版 `f3458758ff13bc77cd33037f9655a1c9df1fee34`。初回は新フロー `SBKB_INTEGRATION_V1` の学習者本人が、有効な現行画面から同一Sessionの観測記録を照合する契約を推奨する。候補の生成世代に関係なく、保存済み受付票が示す事実だけを返す。通常のevents POSTは従来どおり現行の生成元を要求する。

### 照合根拠と既存schema

- `backend/migrations/1790970000000_add_delivery_reliability.js` の `client_event_receipts` は `session_id`、`event_key`（`Idempotency-Key`）、`client_id`（stream UUID）、`client_sequence`、`request_hash`、保存された `event_id` とSession内の `sequence_number` を保持する。主キーは `(session_id, event_key)`、一意制約は `(session_id, client_id, client_sequence)`。`backend/src/research-events.ts` では、研究イベントと受付票を同じ取引で確定する。受付票のない保存経路や、別表 `operation_receipts` の操作結果は対象外。
- `request_hash` は `backend/src/delivery-reliability.ts` の `digest({event,stream,order})`。入力の `event` はパース済みの送信JSON、`stream` と `order` は送信ヘッダー文字列。canonicalはオブジェクトのキーを再帰的に `localeCompare` で並べ、配列順を保持し、キーとスカラーを `JSON.stringify` で表現する。そのUTF-8をSHA-256の小文字hexにする。元のHTTPの空白やキー順に依存しないが、DBに正規化して保存された本文や、日時・省略項目・streamの表記を変えた値からの再計算は使わない。
- 照合元は、キューに残る同じ記録の `JSON.parse(JSON.stringify(item.event))`、送信したstream文字列、既存送信処理と同じ `String(order)`。v2の `observation-outbox.ts` とv3の `observation-stream-v3.ts` の送信箇所が根拠。認証用ヘッダーと元の画面ID・世代はハッシュにも受付票にも含まれない。Sessionとキーはハッシュ外で個別に照合する。完全一致はこの組と要求ハッシュの一致を指し、画面や世代の真正性・送信元端末・ローカルのACKを証明するものではない。ローカルの元値を再現できない記録は照合せず保留する。
- ブラウザーのSHA-256は `frontend/src/client-identity.ts` の `requestDigest` にcanonical済みの文字列を渡せる。これはSHA-256部分を共用するだけで、canonicalは現行サーバーの `digest` に合わせる。`localeCompare` を別のソート順で置き換えず、実装時に対応ブラウザー・言語設定と配信先Nodeで共通ベクトルを照合する。通常観測と入れ子の `VIDEO_SEEK`、キー順違い、省略と値あり、小数、streamの表記違い、連番の文字列を含める。一致を確認した実行条件と観測形式だけでクライアントから送る。比較関数の変更や既存ハッシュの再計算は別契約。

### APIと認可境界

- `POST /api/sessions/:sessionId/observation-receipts/query`。照合条件をURLに残さないためJSON本体を使う。要求は `{contractVersion:1, items:[{eventKey,clientStreamId,clientSequence,requestHash}]}` の閉じた形式で、1–50件、展開後の本体16 KiBまでを初期値とする。既存形式のUUID、`^[1-9][0-9]{0,14}$` の文字列、`^[a-f0-9]{64}$` を検査し、同じ `eventKey`、同じstreamと連番の重複を拒否する。UUIDの重複判定はDB上で同一の表記も拾い、元のstream文字列はハッシュ計算前に変更しない。未知項目・バージョン・不正JSONは固定400、サイズ超過は固定413。認証情報は既存のヘッダーで受け、イベント本文・生成元・自由記述は照合本体に含めない。
- `backend/src/access-control.ts` のBearer認証から本人Sessionを確定し、パスとの一致を検査する。他Session（存在・不存在）、不正なパス、旧protocolや研究者権限によるこの経路へのアクセスは、同じ固定404で受付票を検索しない。本人Sessionは `experiment-participant-access.ts` と `experiment-execution.ts` の条件を再利用し、実施所属、新フローの公開条件、コードのハッシュ・世代、現行画面のsecretと世代、候補の本人所属、RUNNINGを確認する。401（無効・失効したコード）、409（無効化・開始前・終了・旧画面）を受付票結果と分ける。正規切替済みの新画面は同一Sessionで照合でき、旧画面は拒否する。候補の旧生成元を現行画面の証明として使わず、照合経路にevents POSTの生成元一致条件を転用しない。過去Stageの既存受付票は、現在のStageやMapの編集可否で絞らない。
- 本照合は現行の画面検査が済んだ時点の結果とする。入口の検査だけに頼らず、短い `REPEATABLE READ READ ONLY` 取引の同じスナップショットで権限条件を読取りで再評価し、通過後に受付票をSELECTする。現行の `lockCurrentExperimentClient` は `FOR UPDATE` を伴うため、書込み経路と同じ判定条件を共有してSELECT用に分ける。書込み経路のロックは維持する。スナップショット後の切替・失効や通信中の認証変更と競合し得るため、表示する場合も呼出し時に保持した認証revision・画面登録revision・Sessionと応答時を照合し、古ければ結果を適用しない。
- 削除済みコードはこの経路に限り固定410とし、現行の通常経路が返す `queueKey` と破棄指示を含めない。`frontend/src/auth-client.ts` の `apiFetch` はその通知を受けるとキューと回答ドラフトを消去し、`/deletion-ack` を送る。照合クライアントは現行認証ヘッダーを使う読取り専用の呼出しとし、汎用クライアントの削除・報告・再送の副作用を起動しない。明示的な研究データ削除の既存手順は維持する。

### 判定と応答

| 条件 | 応答と意味 |
|---|---|
| 本人Sessionの `event_key`・stream・クライアント連番・`request_hash` がすべて一致し、参照先イベントのSession・イベントID・保存順も一致 | `200` の対象結果を `MATCHED`（受領済みと確認）。初回対象は `schema_version=1`、`actor_type='LEARNER'`、現行の学習者観測イベント種別。 |
| 受付票なし、または同じキーでもstream・連番・ハッシュが異なる | `200` の対象結果を `NOT_CONFIRMED`（一致する受付票を確認できない）。相違した項目や、同じキーの行の有無は返さない。別Sessionにだけ存在する組も本人Sessionでは同じ結果。並行COMMITや対象外の保存経路があるため、未保存の確定には使わない。 |
| 認可状態を読み取れない、タイムアウト、DB障害、または一致した受付票と参照先の観測イベントの整合を確認できない | 要求全体に固定 `503` `observation_receipt_lookup_unavailable`（照合処理に失敗）。部分結果は返さない。通信断・応答不正もクライアントでは照合失敗。 |

SQLは認可済みの `session_id` と要求中のキーで範囲を限定し、型付きパラメーターを使う。参照先は同じSessionで結合し、受付票が一致しているのにイベントが欠落・不整合なら障害扱いにする。応答JSONは `{contractVersion:1, results:[{status: "MATCHED" | "NOT_CONFIRMED"}]}` のみ。入力順に1対1で返し、件数と対応はクライアントでも確認する。イベントID・保存順は内部で検証し、応答には不要。固定の認証・認可エラーも項目単位の結果を含めない。

全応答は `Cache-Control: no-store`。短いDBタイムアウトと接続数制限を設け、本人単位で同時1件と回数上限を設ける案を実測する。制限超過は固定429を返す。アプリ・プロキシ・例外追跡・SQLログにはルート名、固定の結果分類、件数、処理時間だけを残す。要求・応答本文、ヘッダー、Sessionやキー・streamの値、ハッシュ、SQLパラメーター、パーサー例外本文を採取しない。永続監査への追加は別途判断する。

### 実装後の受入条件と追加判断

- 分離した合成環境で初回送信をCOMMITさせ、201を遮断してローカルACKを失わせる。画面の正規切替後、元の記録のdescriptorは現行画面から `MATCHED`。旧画面の照合と、現行画面から旧生成元を提示した通常送信は従来の409。キーを保って本文・stream・連番をそれぞれ変えると、不在と同じ `NOT_CONFIRMED`。未COMMIT時の照合負結果と、COMMIT後の再照合での `MATCHED` を確認する。
- 別Sessionの実在・架空IDへの要求はいずれも同じ404で照合SQLが実行されない。本人パスへ別Sessionのdescriptorを送っても情報が出ない。失効・削除・終了・開始前・古い画面と、途中で権限が切り替わる場合を確認する。照合障害と不在の応答が異なり、過大要求を拒否し、テスト用の識別値がログに出ないことを確認する。
- 成功、不一致、拒否、障害、繰返しの前後で `research_events`、`client_event_receipts`、採番カウンター、配送報告・削除応答確認の表と、IndexedDBのv2/v3の行・保留印・ACK数を照合する。照合経由の新規書込み、再送、ACK化、削除が0件であることを確認する。別経路の `logSaved=false` 警告は照合結果で解除しない。
- 既存の表と索引で実現でき、migrationは不要。確認済みのPR #59の世代拒否とPR #60のACK喪失・同一再送・受付票の照合記録を設計根拠として再利用した。今回、新しいHTTP経路の結合試験は行っていない。
- 実装前に、公開する同一Sessionの読取権限（正規画面切替・新しく有効になった本人コードでも過去記録を照合できる範囲）、ハッシュ互換性の対応環境、上限を確定する。終了後や失効後に照合する必要がある場合は、研究者認証・実施範囲・descriptorの受渡し・監査と終了後の閲覧条件を別途承認する。受付票による元世代の証明が必要なら既存schemaでは足りない。キューへの受領確認の反映、回収、配信、v3有効化は個別に判断する。

### 単位4aの実装前確認（2026-11-18）

#### コード再発行後の照合範囲

- `backend/src/experiment-participant-access.ts` の `authenticateExperimentToken` は現行コードのハッシュから、本人Session・実施所属・コード世代を得る。`lockExperimentProof` は同一Session・実施でコードのハッシュと世代を再検査し、`lockCurrentExperimentClient` は現行画面のsecret・画面世代・その画面登録のSessionとコード世代を確認する。`experiment-execution.ts` は公開条件とRUNNINGも要求する。再発行は旧ハッシュと世代を `experiment_retired_credentials` に残し、同一Sessionのコード世代・画面世代を繰り上げ、現行画面の登録を解除する。旧コードは401。新コードも画面登録が成立するまで照合できない。通常の画面切替だけではコード世代は変わらない。
- 現行のイベント新規保存と再発行は同じ参加者アクセス行のロックで直列化するが、受付票と参照先イベントには保存を許可したコード世代・画面世代への結びつきが残らない。受付票に作成時刻はない。`research_events.server_timestamp` と `experiment_retired_credentials.revoked_at` や発行操作の時刻は参考にできるが、いずれも壁時計による記録であり、同時刻・時計の補正・取引の境界を含め、保存を許可した世代を示す値ではない。既存schemaで受付票ごとに再発行の前後を権限判定に使える確実さで分類することはできない。streamは画面候補IDと別のUUIDであり、ローカルの生成元・連番からも世代を補完しない。

| 案 | 確認できる範囲と必要な変更 | 利用者への影響 |
|---|---|---|
| 現行コードと現行画面で同じSessionの完全一致を照合（推奨） | 元のdescriptorを保持していれば、再発行前後を問わず既存受付票を照合できる。schema変更は不要。照合権限の単位はSessionで、過去のコード利用者と同一人物であることの証明はできない。 | コード再発行後も受領確認を続けられる。研究者が同じSessionの新コードを別の利用者へ渡す運用では、元のdescriptorを得た新利用者が受領の有無を確認できるため、その権限を許容するか判断が必要。 |
| 現行コード世代だけに制限 | 将来の受付票へ、保存取引内で検証した `credential_generation` を保持し、現行世代と比較する契約とschema変更が必要。新規行への保存だけを追加し、既存行は世代不明のままにする。既存行を改変せず厳格に運用する場合は、世代不明行を照合対象外にするか、再発行済みSessionの照合全体を止める。 | 再発行後の利用者が旧世代の受領を確認できる範囲を狭められる。既存受付票を含む制限では、同じ本人でも正規のACK喪失を自己解決できない。再発行済みSession全体を止める場合は、再発行後の保存分も照合できない。 |

両案とも本人Sessionを認証から確定し、他Sessionの実在・不存在は同じ404、本人Sessionで一致しないdescriptorは同じ `NOT_CONFIRMED` とする。キーによる列挙や、世代不明・不一致の詳細は返さない。コード再発行が同じ参加者の再入場のみを指すのか、別の利用者への権限移転を含み得るのかを運用側で決める。後者を許容するなら、世代制限の契約を承認するまでコード世代をまたぐ照合の実装を保留する。終了後・コード失効後に照合する研究者向け権限と監査は別の判断とする。

#### ハッシュの互換性と限定検証

- 既存 `research-events.ts` は `digest({event,stream,order})` を、DB保存前のパース済みJSONと元のヘッダー文字列から計算する。Windows上のNode 22.23.5（ICU 78.3）で既存 `delivery-reliability.ts` の `digest` を直接実行し、分離したEdge 157.0.4341.60のページで、現行canonicalを写した検証コードから実際の `client-identity.ts` の `requestDigest` を呼んだ。合成19入力（観測形式11、形式外の境界8）が両実装で一致した。Edgeの `navigator.language` をen-US・ja-JP・sv-SEに変えても、実測した既定collatorはNode・Edgeともja-JPだった。
- JSONの空白、外側と入れ子のキー順、同じJSON数値にパースされる指数表記と負のゼロ、シリアライズで省略される `undefined` は一致した。丸めていない異なる小数、同一時刻を表す異なる文字列、値の有無、stream UUIDの大文字表記、異なる連番文字列でハッシュが変わった。形式外の境界入力では、Unicodeリテラルと同じ文字列を表すエスケープは一致し、合成済み文字と結合文字、配列順、明示的なnullと省略、数値の連番と文字列の連番は異なった。
- 言語を明示した `localeCompare` も補助試験した。en-US・ja-JP・sv-SEすべてで観測形式11入力が既存Nodeと一致。形式外の非ASCIIキー（`ä` と `z` を含む）だけはsv-SEで順序が変わり、全体では18/19だった。任意JSON・任意のICU・実配信環境でのハッシュ互換性は未確認。実配信のNodeイメージと対象端末で同じ検証を通した観測形式に限定する。観測形式やsortの対象が増える場合は改めて照合する。
- 元のイベント値・stream表記・連番文字列が欠ける、非対応形式、実行環境の互換性未確認、計算失敗のいずれかなら、ブラウザーはその項目の要求を送らず「照合できない」とし、元行を未確認のまま保持する。異なる言語設定や入力値の候補を試して一致を探さない。正しく計算できたdescriptorへの応答は既定の `MATCHED` / `NOT_CONFIRMED` を使い、API・通信障害は照合失敗として区別する。限定検証はDB・キューに接続せず、API実装を伴わない。再現コードはGit管理外の `.local/observation-stream-v3/receipt-hash-compat-probe.mts` に置いた。

#### 追加の受入条件

- 同一Sessionで、再発行前後にそれぞれ受付票を合成し、承認された案の範囲だけ一致することを確認する。再発行前と再発行後にACK応答喪失を入れ、新コードと新画面の組、旧コード、未登録画面、旧画面、正規の同一コード内画面切替を区別する。同一キー異内容は両案で、世代不明の既存行は世代制限案で、受領済みにならないことも確認する。別Session・終了・認証切替中の遅延応答・障害の検証と、DBおよびキューの不変条件は単位4aどおり。
- 実配信のNodeイメージと対象ブラウザーで、上記の共通ベクトルと現行の正規観測キーの組（画面・休止再開・動画・FB）を照合する。実APIの合成イベントを保存した受付票でも、ブラウザー側の元記録から作ったハッシュの一致を確認する。非対応の条件で要求・ACK・削除が生じず、既存のハッシュと受付票が維持されることを実装の受入条件とする。

### 単位4aの実装と検証（2026-11-18）

- 合意した運用は、コード再発行を同じ参加者の再入場に限り、別の参加者には新規Sessionを作ること。`docs/experiment-participant-access-r08.md` に明記した。受付票は保存当時のコード世代や画面の真正性を証明しない。
- `POST /api/sessions/:sessionId/observation-receipts/query` を実装した。現行コードの認証と本人Sessionの範囲確認を行い、read-onlyのREPEATABLE READトランザクションで現行画面・コード世代・実施所属・RUNNINGを再検証してから照合する。照合は1～50件、JSONは16 KiB以下、Sessionごとに同時1件・1分30回、プロセスごとに同時8件まで。照合専用接続は最大4、取得・SQLに2秒の上限を設定した。例外本文・認証値・記録内容はログへ渡さない。削除済みコードへの410にはキュー消去指示を含めない。
- 認可済みSessionの受付票を、冪等キー、stream、クライアント連番、現行形式の要求ハッシュで照合する。一致した場合は、保存済みイベントのSession・ID・保存順と学習者の観測形式も検査する。応答は入力順の `MATCHED` または `NOT_CONFIRMED`。DBタイムアウトまたは整合性を確認できない場合は固定503。既存ハッシュ・受付票・schemaの変更はない。照合結果で新しい送信、ACK、キュー変更を起動する画面は追加していない。
- Node 22 Alpine（22.23.5）のAPIとPostgreSQL 17の専用模擬DBを別ネットワークで起動し、通常と同じViteの同一オリジンプロキシを使うWebコンテナからEdge 157で検証した。実APIの201を保存後に遮断し、再発行前後の受付票を現行コード・現行画面で確認できた。旧コード、未登録・切替前画面、別Session、研究者、実施終了後を拒否した。キーが同じでも本文・stream・連番が異なる場合は不在と同じ応答で、壊れたJSONと上限超過も拒否した。模擬DBの受付票表を一時的にロックして固定503を確認し、解放後に再照合できた。
- Webコンテナ経由では、通常観測のハッシュ11件（実APIに保存した要求を含む）がブラウザーとサーバー実装で一致した。v2/v3の合成キュー全行と保留印・ACK累計、DBの対象テーブルの件数と指紋は照合前後で一致した。ハッシュ互換性の確認対象はこのNode/Edge構成と現行の観測形式。別のランタイムや未対応形式を利用する場合は互換性を確認し、元値を再現できない記録は未確認で保持する。参加者端末での利用、旧記録のACK化・回収、研究者向け照合、配信は後続工程。
- 検証コマンドは `npm run db:mock -- verify-receipt-lookup --name <新規模擬DB名>`。配信と同じWeb/APIイメージを使う場合は、専用環境のループバックURLを `MOCK_RECEIPT_API_BASE` と `MOCK_RECEIPT_WEB_BASE` に渡せる。通常のスイートにも照合試験を登録した。選択回帰はDB分離ガード、配送、観測生成元、受付票照合、参加者認可の5件がNode 22.23.5で成功。初回は既存の配送試験が要求する固定模擬Kitを入れておらず外部キーエラーで停止した。既存seedを専用DBだけに適用して再実行した。バックエンドの型検査・build、変更対象のLint、差分チェックは成功した。専用DBは識別情報と接続数0を確認して削除した。
